## 0. 순서 (261023에 정함)

**기능 확장 2-1(규정과 선수 데이터 잇기)을 먼저 한다.** 검색은 2-1에 필요한 것만 같이 한다.

1. **경계 질문을 시험 문항에 넣기** (1절 첫 항목). 반나절 일이다. 방금 넣은 분야 판별을
   손으로만 확인한 상태라, 2-1에서 검색을 더 건드리기 전에 이걸로 지켜 둔다.
2. **2-1을 부상자 명단 질문 하나로 시작한다.** 데이터 출처(약관 확인 포함)를 먼저 정하고,
   그다음 부상자 명단 -> 외국인 교체 -> FA 순서로 넓힌다. FA가 데이터가 가장 많이 든다.
3. 1절의 나머지 검색 항목은 2-1을 하다가 막히는 곳부터 꺼내 쓴다. "못 찾음 기준"과
   "질문 나누기"는 2-1에서 어차피 필요해진다.
4. 2-2(판정 해설)는 2-1이 돌아간 뒤에 한다. 데이터 구하기가 더 어렵다.

이렇게 정한 이유:

- **검색은 이미 쓸 만한 수준이다.** 46문항 모두 정답이 AI에게 넘어간다(상위 8개 안 100%).
  남은 검색 항목은 1등 비율을 조금씩 올리는 일이라, 사용자가 느끼는 차이가 작다.
- **"왜 이 앱을 써야 하나"는 검색을 다듬어서는 풀리지 않는다.** 규칙집에서 조항을 더 잘 찾는 건
  PDF 검색과 정도 차이일 뿐이다. 특정 선수에게 규정을 적용한 답은 다른 서비스가 주지 않는다.
- **2-1의 근거 규정은 오늘로 다 갖춰졌다.** 규약(FA, 외국인선수)을 넣었고 부상자 명단은 리그
  규정에 있다. 지금 막힌 건 선수 데이터뿐이다.

**단, 답변 채점 결과에 따라 바뀔 수 있다.** 261023 규약 연결과 분야별 색인 뒤의 `eval:answer`를
아직 못 쟀다(NVIDIA 무료 API의 답변 모델이 응답하지 않았다). 재 봐서 답변 정확도가 이전
측정보다 크게 떨어졌으면 그 원인(검색 쪽)부터 고친다.

## 1. 검색 능력 향상

지금 상태(261023, 46문항): 정답이 1등 29개(63%), 상위 8개 안 46개(100%).
1등 비율이 문항이 늘 때마다 내려가고 있다(77% -> 63%). AI는 상위 8개를 다 보지만,
정답이 아래에 있으면 작은 모델이 위쪽의 엉뚱한 조항을 붙잡는다.

- [ ] **경계 질문을 시험 문항에 넣기.** 분야 판별(`docs/search.md` 2-4)을 손으로만 확인했다.
  `외국인 선수도 비디오 판독 신청할 수 있어?`, `부상자 명단에 올리면 며칠 뒤에 돌아와?`,
  `승부조작하면 어떻게 돼?`, `엔트리 몇 명이야?`, `경기 중에 선수 퇴장당하면 벌금 있어?`.
  분야 판별 값(`DOMAIN_MIDPOINT`, `OTHER_DOMAIN_FLOOR`)을 고칠 때 이게 있어야 잴 수 있다.
- [ ] **규약 쪽 은어를 사전에 넣기.** `연봉조정`(규약은 `연봉중재`), `트레이드`(규약은
  `선수계약의 양도`, `트레이드`는 2개 조항뿐). 넣을 때마다 시험 문항도 같이 늘린다.
- [ ] **사람 말 설명을 더 많은 조항에 붙이기.** 상황을 풀어 쓴 질문이 몰리는 곳부터.
  아웃(5.09), 주루(5.06), 득점(5.08). 지금은 2개 조항뿐이다(`docs/search.md` 한계 7).
- [ ] **질문 말투 제외로 내려간 2문항 보기.** `낫아웃이 성립하는 경우는?` 3등 -> 5등,
  `비디오 판독은 몇 번까지` 3등 -> 4등(`docs/search.md` 2-1).
- [ ] **글자만 쓰는 비상 경로 확인.** 임베딩 API가 실패하면 분야를 나누지 않고 검색한다.
  직접 실행해서 확인한 적이 없다.
- [ ] **"못 찾음"을 알아내는 기준.** 지금은 검색이 실패해도 조항 8개를 꽉 채워 넘긴다
  (`docs/search.md` 한계 4). 기능 확장에서 질문을 규정/선수 데이터로 나눠 보낼 때도 필요하다.
- [ ] **리그 규정 부록 하나를 못 읽고 있다.** `2026년 구단별 경기관리인...`. 담당자 명단이라 우선순위 낮음.

## 2. 기능 확장

규칙집 검색만으로는 "규칙집 PDF를 직접 찾아보면 되지 않나?"에 답하기 어렵다.
다른 서비스가 하지 않는 일, **규정을 실제 선수와 경기에 적용해 주는 것**으로 넓힌다.

### 2-1. 규정과 선수 데이터를 잇기 (먼저 한다)

"○○ 선수 FA 언제 돼?", "이 선수 부상자 명단에서 언제 돌아올 수 있어?",
"외국인 선수 교체 몇 번 남았어?" 같은 질문에 답한다. 시즌 중과 스토브리그에 실제로
자주 나오는 질문이라 이 앱을 써야 하는 이유가 분명해진다.

근거 규정은 이미 다 들어 있다. 선수 데이터만 더하면 된다.

| 질문 | 근거 규정 | 필요한 선수 데이터 |
|---|---|---|
| FA 언제 돼? | 규약 제162조 (8 정규시즌, 대졸 7, 1시즌 = 현역 등록 145일 이상 등) | 시즌별 현역 등록일수, 첫 등록 연도, 대졸 여부, 다년계약 기간 |
| 부상자 명단에서 언제 돌아와? | 리그 규정 제14조-3 (10·15·30일 중 택일, 시즌 최대 30일) | 부상자 명단 등재일과 기간, 그 시즌 등재 이력 |
| 외국인 선수 교체 몇 번 남았어? | 외국인선수 고용규정 제9조 (해지 후 추가등록 2회, 아시아쿼터 1회) | 구단별 그 시즌 외국인 계약 해지·추가등록 이력 |

- [ ] **데이터 출처 정하기.** 공개 API는 없다. 261023에 확인한 결과 공개 사이트는 전부 자동 수집이 막혀 있다.
  - KBO 공식(koreabaseball.com) robots.txt: "본 사이트의 데이터를 사전 승인 없이 자동 수집·크롤링·복제하는
    행위를 금지합니다", 검색엔진 외 모든 봇 `Disallow: /`. **사전 승인을 받으면 길이 있다는 뜻이다.**
  - 네이버 스포츠: 검색엔진 외 `Disallow: /`.
  - 스탯티즈: Cloudflare가 봇 차단.
  - 비공식 수집 코드 [KBO-Data-Portal](https://github.com/KBO-Data-Portal)(MIT)도 결국 위 사이트를 긁는다.
  - 남은 길: KBO에 데이터 이용 승인 문의, 유료(Sportradar는 KBO 공식 데이터 파트너, 엔트리 변동이 들어
    있는지는 미확인), 또는 사용자가 선수 상황(등재일, 기간 등)을 말하면 규정대로 계산해 주는 방식.
  - **261023 결정:** 사용자는 선수 이름만 말하고, 앱이 네이버 뉴스 검색 API로 찾아 출처와 함께 답한다.
    공식 데이터 문의는 따로 넣어 둔다. 경위는 `docs/feature.md`.
- [ ] **세 질문 중 하나로 시작하기.** 부상자 명단이 가장 작다(등재일 + 기간만 있으면 계산된다).
  FA는 시즌별 등록일수가 수년치 필요해 데이터가 가장 많이 든다.
- [ ] **질문 나누기.** 선수 이름이 든 질문은 선수 데이터 조회 + 규정 검색, 없는 질문은
  지금처럼 규정 검색만. 이름 인식은 선수 명단과 대조한다.
- [ ] **계산은 코드로, 설명은 모델로.** "FA까지 남은 시즌"처럼 숫자가 나오는 부분은 코드가
  규정대로 계산하고, 모델은 그 결과와 근거 조항을 받아 설명만 한다. 작은 모델은 조항을
  상황에 대입하는 걸 자주 틀린다(`docs/search.md` 한계 8).
- [ ] **시험 문항.** 선수 데이터 질문용 문항과 정답(계산 결과)을 따로 만든다.

### 2-2. 실제 판정을 해설하기

"어제 그 장면은 왜 아웃이야?"에 그 경기 상황과 해당 조항으로 답한다. 판정 논란이
생기는 순간에 찾아오게 만들 수 있다. 2-1보다 데이터를 구하기가 어려워 뒤로 둔다.

- [ ] **경기 데이터 출처 정하기.** 문자 중계(KBO 공식 사이트, 포털)가 후보다. 공개 API는 없고
  상용(Sportradar 등)은 유료다.
- [ ] **장면을 상황으로 바꾸기.** 문자 중계 한 줄에서 아웃카운트, 주자 위치, 타구 종류를
  뽑아야 규칙 검색이 된다. 지금 검색은 상황을 풀어 쓴 질문에 약하다(`docs/search.md` 한계 7).
  1절의 "사람 말 설명 늘리기"가 여기에도 그대로 도움이 된다.
- [ ] **어느 장면인지 고르는 화면.** 사용자가 "어제 그 장면"을 말로 설명하는 대신 경기와
  이닝을 고르게 한다.
