# 답변 모델과 응답 처리 기록

이 문서는 AI 답변을 만드는 쪽(모델 선택, 시간 제한, 재시도, 끊김 처리)에서 무엇을
겪었고 무엇을 시도했는지 남긴 기록이다. 검색 쪽은 `docs/search.md`에 따로 적는다.
모델이나 시간 설정을 바꾸기 전에 읽고, 바꾼 뒤에는 이 문서를 갱신한다.

| | |
|---|---|
| 마지막 갱신 | 2026-10-07 |
| 관련 코드 | `lib/llm.ts`, `lib/conversation.ts`, `lib/clarify.ts`, `app/api/chat/route.ts`, `app/api/report/route.ts`, `app/page.tsx`, `app/chat-history.ts`, `lib/answer-done.ts` |
| 측정 | `scripts/eval-answer.mjs` (`npm run eval:answer`) |

### 환경변수

| 이름 | 필수 | 뜻 |
|---|---|---|
| `NVIDIA_API_KEY` | 예 | build.nvidia.com 키. 계정 전체에 쓰인다(모델마다 다르지 않다). 따옴표나 `;` 없이 `nvapi-...`만 |
| `NVIDIA_MODEL` | 아니요 | 답변 모델. 없으면 `openai/gpt-oss-20b` |
| `NVIDIA_EMBED_MODEL` | 아니요 | 검색용 임베딩 모델. 없으면 `nvidia/nemotron-3-embed-1b` |
| `REPORT_WEBHOOK_URL` | 아니요 | 틀린 답 신고를 보낼 디스코드/슬랙 웹훅 주소. 없으면 서버 로그에만 남는다(Vercel 무료 플랜은 1시간 보관) |

## 1. 지금 구조

NVIDIA build.nvidia.com의 **무료** OpenAI 호환 API를 쓴다.
모델은 `openai/gpt-oss-20b`. 환경변수 `NVIDIA_MODEL`로 바꿀 수 있다.
(Vercel에 `NVIDIA_MODEL`이 있으면 코드 기본값보다 우선한다.)

### 시간 제한

| 구간 | 제한 | 넘으면 |
|---|---|---|
| 첫 글자까지 | 20초 (`FIRST_TEXT_MS`, 재시도 포함) | 포기하고 검색된 조항만 보여준다 |
| 글이 나오는 중 | 전체 제한 없음. 새 글이 3초(`STALL_MS`) 안 오면 끊는다 | 받은 글은 남기고 "답변이 중간에 끊겼습니다 · 다시 시도" |
| Vercel 함수 | 300초 (`maxDuration`, 무료 플랜 최대) | 강제 종료 (화면은 끊김으로 처리) |

### 끊김 알아채기

서버는 답을 끝까지 썼을 때만 끝에 `\u0004`(`ANSWER_DONE`)를 붙인다.
이 표시 없이 닫히면 화면은 끊긴 것으로 본다. 서버가 멈췄든, 토큰 한도(900)에 걸렸든,
Vercel이 함수를 끝냈든, 연결이 끊겼든 한 가지 방법으로 잡힌다.
끊긴 쪽이 "끊겼다"고 알리는 방식은 함수가 강제로 끝나면 보낼 수가 없어서 이렇게 했다.

### 재시도

두 겹이다.

- **SDK (`maxRetries: 3`)**: HTTP 503·429를 0.5·1·2초 기다렸다 다시 부른다.
- **라우트 (`RETRY_DELAYS_MS`)**: 한 글자도 못 받았으면 0.5·1·2·4초 기다렸다 다시 부른다.
  첫 글자 20초 시한을 넘기지 않는 만큼만 한다.

라우트 쪽이 필요한 이유는 3절 "과부하가 HTTP 200 안에 실려 온다"에 있다.

## 2. 260929 — 배포본에서 답이 중간에 잘리던 것

### 원인 1. 우리가 스스로 60초 제한을 걸고 있었다

`app/api/chat/route.ts`에 `maxDuration = 60`이 있었다. 주석은 "Vercel 무료 플랜의 기본
제한이 짧아서 늘린다"였는데, 지금 Vercel 무료 플랜은 **기본값도 최대값도 300초**다.
60은 오히려 줄이고 있었다. 300으로 올렸다.

### 원인 2. 무료 API가 쓰다가 멈춘다

측정 기록(`results/answer-*.json`)에서 잘린 답을 찾아보니 토큰 한도(900)에 걸린 답은 없었다
(100~270토큰). 확실히 잘린 5건은 모두 측정 스크립트의 20초 대기 한계에 걸린 것이었다.
무료 서버가 느려지거나 멈춘 것이다.

그래서 **전체 시간 대신 글이 멈춘 시간으로 끊도록** 바꿨다(1절 표).
멈춤 기준은 15초 -> 5초 -> 3초로 줄였다. 정상일 때 조각은 0.1초 안팎으로 오고,
멈췄다는 신호가 따로 오지 않아 글이 멎은 채로 사용자를 오래 세워두지 않는 게 낫다.
실제 모델로 잰 조각 사이 최대 공백은 nemotron-3-super 0.2~0.3초, gpt-oss-20b 0.7초(33문항)였다.

가짜 NVIDIA 서버(`next dev` 프로세스의 fetch를 가로채는 스크립트)로 여섯 상황을 확인했다.

| 상황 | 결과 |
|---|---|
| 정상 | 끝까지 받고 완료 표시 |
| 2초마다 한 조각씩 40초 | 끊기지 않고 끝까지 |
| 쓰다가 멈춤 | 마지막 글 3초 뒤 끊김 표시 |
| 토큰 한도에서 잘림 | 끊김 표시 |
| 응답 시작이 25초 | 20초에 포기, "AI가 20초 안에 답을 시작하지 못했습니다" |
| 추론만 하고 글이 안 나옴 | 20초에 포기, 재시도 안 함 |

### 참고: OpenAI SDK의 `timeout`은 응답 헤더까지만 걸린다

openai 7.9.0의 `fetchWithTimeout`은 fetch가 헤더를 받으면 타이머를 푼다.
스트림이 흐르는 동안은 SDK 제한이 없다. 흐르는 중에 `signal`을 끊으면 스트림은
**에러 없이 그 자리에서 끝난다**(`isAbortError`면 조용히 return). 그래서 끊겼는지는
`signal.aborted`로 따로 본다.

## 3. 260929 — 모델을 바꿨다가 되돌린 것

### 모델 목록은 키 없이도 보이지만, 목록에 있다고 쓸 수 있는 건 아니다

`GET https://integrate.api.nvidia.com/v1/models`는 키 없이 81개를 돌려준다.
하지만 키 없이 호출하면 **되는 모델도 막힌 모델도 똑같이 401**이라 구분이 안 된다
(존재하지 않는 이름만 404). 키를 넣고 불러봐야 안다.

**키는 모델마다 다르지 않다.** 어느 모델 페이지에서 "Get API Key"를 눌러도 계정 전체 키가
나온다. nemotron-3-super 페이지에서 받은 키로 임베딩 모델도 불렸다.

### 그날 실제로 불러본 결과

| 모델 | 결과 |
|---|---|
| `openai/gpt-oss-20b` | 오전엔 모든 호출이 20~60초 무응답. 오후엔 다시 응답 |
| `nvidia/nemotron-3-super-120b-a12b` | 응답함. 요청의 20~30%를 과부하(503)로 거절. 헤더에 `deprecation: 2026-10-03` |
| `deepseek-ai/deepseek-v4.1-flash` | 짧은 인사엔 응답. 실제 질문엔 35~45초 추론만 하다 토큰 한도, 본문 0자 |
| `google/gemma-4-31b-it` | 20초 무응답 (5번 모두) |
| `nvidia/nemotron-3.5-lightning-30b-a3b` | 20초 무응답 (5번 모두) |
| `nvidia/nemotron-nano-3-30b-a3b` | 404 (이 계정에서 막힘) |
| `nvidia/llama-3.1-nemotron-70b-instruct`, `nvidia/nemotron-4-340b-instruct` | 안 불러봄. 2024년 모델이고 70B·340B를 전부 계산해 느리다. 340B는 입력 한도가 4K 토큰이라 조항 8개를 못 넣는다 |

### nemotron-3-super로 바꿨다가 되돌렸다

gpt-oss-20b가 응답하지 않아 바꿨다. 같은 21문항에서 정확도는 같았다.

| | gpt-oss-20b (260913 기록) | nemotron-3-super (260929) |
|---|---|---|
| 필요한 내용을 전부 말함 | 16/21 | 16/21 |
| 채점 항목 | 48/56 | 49/56 |
| 평균 시간 | 5.8초 | 7.9초 |

그 뒤 응답 헤더에서 `deprecation: 2026-10-03`을 발견했고, gpt-oss-20b가 다시 응답해서 되돌렸다.
**다음에 모델을 고를 때는 응답 헤더의 `deprecation`부터 본다.**

### 실수: 첫 비교는 검색이 망가진 채로 쟀다

처음엔 "nemotron이 더 정확하다(22/29 -> 24/29)"는 결론을 냈다. 그런데 그때 개발 서버의
임베딩 호출이 전부 401이라 **검색이 글자 검색만으로 돌고 있었다.** 조건이 다른 두 기록을
비교한 것이다. 검색을 고치고 다시 재자 위 표처럼 같았다.

401의 원인은 `.env.local`의 키 줄이 `NVIDIA_API_KEY='nvapi-...';`처럼 **끝에 세미콜론**이
붙어 있던 것이다. Node의 `process.loadEnvFile`(측정 스크립트)은 세미콜론을 무시하고 읽었고,
Next.js는 따옴표와 세미콜론까지 키로 읽었다. 그래서 스크립트로 직접 부를 때는 되고 앱에서만
안 됐다. **측정 전에 개발 서버 로그에 `임베딩 실패 401`이 없는지 먼저 본다.**

### 과부하가 HTTP 200 안에 실려 온다

nemotron-3-super의 과부하는 두 가지로 온다.

- HTTP 503으로 곧바로(0.1초) 거절 -> SDK 재시도가 잡는다.
- **HTTP 200으로 스트림을 연 뒤 첫 이벤트에 `{"error": {"code": 503, ...}}`** -> SDK 재시도는
  상태 코드만 봐서 못 잡는다. 같은 질문 5번 중 2번이 이렇게 빈 답으로 끝났다.

뒤쪽 때문에 라우트에 재시도를 따로 넣었다(1절). 넣은 뒤 같은 질문 8번이 모두 답을 냈다.

SDK 재시도 횟수는 3번으로 뒀다. 30문항 기준으로 재시도 없이 8~9개 실패, 3번이면 3개,
5번이면 오히려 7개였다. 과부하가 15초 넘게 이어지는 때가 있어 늘려도 소용이 없고,
늘릴수록 첫 글자 20초만 잡아먹는다.

### 모델마다 조항 번호 적는 방식이 다르다

nemotron-3-super는 대괄호로 적으라고 해도 네 번에 한 번꼴로 `(정의-40, 주1)`처럼 괄호로 적었다.
(대괄호 인용 비율: gpt-oss-20b 28/30, nemotron 약 70~75%)
화면은 대괄호만 눌러볼 수 있게 되어 있었다. 괄호 안에 검색된 조항 번호가 있을 때도 눌러볼 수
있게 바꿨다(`app/page.tsx`의 `BRACKET`). 모델을 되돌린 뒤에도 그대로 뒀다.

## 4. 261006~07 — 끝내기 질문과 프롬프트, 신고 버튼

### 같은 질문에 답이 갈린다

"5:5 9회말, 주자 둘에 안타면 6:5로 끝나나 7:5로 끝나나?"(정답 6:5, 7.01⒢⑶). 사용자가
물을 때마다 맞기도 틀리기도 했다. 검색은 매번 정답 조항을 넘긴다(7.01이 2등, 9.06⒡가 6등).
`temperature: 0`이어도 NVIDIA 서버의 답은 매번 같지 않다.

| | 맞음 | 평균 시간 |
|---|---|---|
| 앱으로 8번 (`reasoning_effort: low`) | 5/8 | 10초 |
| 직접 호출 8번 (low) | 6/8 | 11초 |
| 직접 호출 8번 (`medium`) | 7/8 | **72초** (최대 200초) |

생각을 늘리면 나아지지만 첫 글자 20초 제한을 거의 항상 넘긴다. 쓸 수 없다.

틀리는 모양은 셋이었다. (1) 타자까지 들어온다고 보고 8:5, (2) 조항을 받고도
"찾지 못했습니다", (3) 맞게 답해놓고 끝에 "규칙집에서 찾지 못했습니다"를 습관처럼 붙임.

### 프롬프트를 고쳤다

- "조항에 없는 내용은 ... '찾지 못했습니다'라고 답하라" ->
  "조항으로 답할 수 없으면 ... 한 문장만 써라. 조항으로 답했다면 이 문장을 붙이지 마라."
- 상황형 질문(단어형이 아닌 것)은 "첫 문장에 결론, 예/아니오면 그것부터, 결론과 다른
  말로 끝내지 마라"를 더했다. 라인드라이브 질문에서 "베이스를 태그하면 아웃"이라고 해놓고
  "태그 없이 지나갈 수 없습니다"로 끝내는 답이 나왔기 때문이다.

`eval-answer`에 `결론먼저` 프리셋으로 넣었고, (3)을 세는 "답 끝에 찾지 못함 덧붙임" 지표를
더했다. 260929 측정을 다시 채점하니 33문항 중 2건이었다.

같은 시간대에 34문항을 번갈아 쟀다(261007). 그날 무료 API가 느려 양쪽 다 3~4문항이
첫 글자 20초를 넘겨 빈 답이 됐으므로, 양쪽 다 답이 나온 29문항끼리 비교한다.

| | 형태별 (이전) | 결론먼저 (채택) |
|---|---|---|
| 필요한 내용을 전부 말함 (29문항) | 22 | 23 |
| 채점 항목 (29문항) | 65/75 | 66/75 |
| 답 끝에 "찾지 못했습니다" 덧붙임 (34문항) | 3 | **0** |
| 조항 받고도 "찾지 못했습니다" (34문항) | 1 | 0 |

정확도 차이 1개는 편차 안이다. 노린 것((3) 덧붙임)은 없어졌고 나빠진 것은 없다.
판정이 갈린 답을 읽어보면, 끝내기 질문은 결론먼저 쪽이 "일부"로 채점됐지만 "예, 6:5로
확정됩니다 ... 이후 득점은 인정되지 않는다"로 내용은 맞았다(채점 키워드 "종료"가 없었을
뿐). `인필드 플라이는 언제 선언돼?`는 결론먼저 쪽이 성립 조건을 빠뜨렸고(3/4 -> 2/4),
`타임`과 `몰수경기`는 결론먼저 쪽이 빠졌던 내용을 채웠다.

(1)·(2)는 7.01⒢에 사람 말 설명(`data/plain.json`)을 붙이면 줄어들 것으로 보였지만
하지 않았다. 설명은 시험에서 틀린 질문에 맞춰 쓰기 쉽고, 규칙집에 없는 해석이 섞이면
"규칙집만 근거로 답한다"가 깨진다. 꼭 필요한 조항에만, 원문을 풀어 쓴 것만 넣는다.

### 틀린 답 신고 버튼

답 아래 "틀렸어요"를 누르면 `/api/report`가 질문, 답, AI에게 넘긴 조항 번호(상위 8개),
모델 이름을 `REPORT_WEBHOOK_URL`로 보낸다. 넘긴 조항 번호가 있어야 틀린 게 검색 탓인지
모델 탓인지 가를 수 있다.

- 주소에 `discord.com/api/webhooks`가 있으면 디스코드 형식(`content`, 2,000자까지 자름),
  아니면 슬랙 형식(`text`)으로 보낸다.
- 누구나 이 주소로 보낼 수 있어서: 다른 사이트에서 온 요청(Origin이 다름)은 거절하고,
  질문 1,000자·답 4,000자로 자르고, 신고 내용 속 `@everyone`·`<!channel>`이 실제로 울리지
  않게 막는다(디스코드 `allowed_mentions`, 슬랙은 꺾쇠를 풀어 씀). 스크립트로 직접 보내는
  도배는 막지 못한다.
- 서버 로그에도 남기지만 Vercel 무료 플랜은 1시간만 보관한다. 그래서 웹훅이 필요하다.

### 대화는 탭을 닫으면 사라진다

`app/chat-history.ts`가 대화를 `localStorage`에서 `sessionStorage`로 옮겼다. 새로고침하면
이어지고, 탭을 닫았다 열거나 새 탭으로 열면 새 대화다. 예전 `localStorage` 기록은 처음
읽을 때 지운다. 틀린 답이 대화와 함께 사라지므로 위 신고 버튼과 같이 넣었다.

## 5. 261007 — 대화 이어받기, 되묻기, 근거 먼저

### 대화를 이어받는다

전에는 질문마다 따로 처리해서 "그럼 2아웃이면?"을 물으면 AI가 무엇을 묻는지 몰랐다.
이제 화면이 앞에서 답을 받은 질문 2개(`HISTORY_LIMIT`)를 같이 보낸다(`lib/conversation.ts`).

- **검색:** 앞 질문들을 이번 질문 앞에 붙여 검색한다(`searchInConversation`). 이번 질문만으로
  한 검색과 섞는 방식은 전부 나빴다(아래 표). "2아웃"만으로 검색하면 그 말이 든 아무 조항이나
  1등이라 섞는 순간 정답이 밀린다.

  | 합치는 방식 | 그럼 2아웃이면? | 되물음에 대한 대답 | 상관없는 새 질문 |
  |---|---|---|---|
  | 높은 쪽 (붙인 쪽 ×0.9) | 29등 | 7등 | 4등 |
  | 높은 쪽 | 12등 | 7등 | 5등 |
  | 평균 | 21등 | 2등 | 5등 |
  | **붙인 것만 (채택)** | **2등** | **6등** | **6등** |

- **AI:** 프롬프트에 "# 이전 대화"를 넣고, 이어지는 질문이면 앞 상황을 이어받고 새 질문이면
  무시하라고 한다.
- 측정(앞 대화를 고정해 둔 이어지는 질문 3개)에서는 세 프롬프트 모두 "그럼 2아웃이면?"을 맞혔다.
  화면에서 직접 해보니 첫 답이 틀리면 그걸 그대로 이어받고, 새 정보("1루에 주자 있고 1아웃이야")를
  무시하고 첫 답을 글자 그대로 되풀이한 일도 있었다.

### 되묻기는 지시문으로는 나오지 않는다

상황이 빠져 답이 갈리는 질문에 "확인이 필요합니다:"로 되묻게 했다(`lib/clarify.ts`, `CLARIFY_RULE`).
화면은 되물음을 하늘색 상자("조금 더 알려주세요")로 보여주고 입력창으로 커서를 옮긴다.

하지만 애매한 질문 2개(testset `clarify: true`)에서 **한 번도 되묻지 않았다.**

- `포수가 세 번째 스트라이크를 놓쳤는데 타자가 1루로 뛰면 살 수 있어?` — 정답 5.05⒜⑵에는
  "1루에 주자가 없을 때, 또는 있더라도 2아웃일 때"라는 조건이 있다. 모델은 그 조항 대신
  기록 규칙(9.15)의 조건 없는 문장을 집어 "예, 안전하게 진루할 수 있다"고 단정했다.
  **조건을 못 읽으니 답이 갈린다는 걸 모르고, 그래서 되물을 이유가 없다.**
- `타자가 친 공이 주자 몸에 맞았는데 그 주자 아웃이야?` — 정답 5.09⒝⑺이 검색 10등이라 넘어가지
  않았다. 조건이 적힌 조항을 못 봤으니 역시 되물을 수 없다.

지시문은 남겨뒀다(점수 차이가 편차 안이고, 되묻기가 나오면 화면이 받아준다). 다음 시도는
지시 대신 **예시**를 프롬프트에 넣는 것이다. 모델은 지시는 무시해도 예시는 따라 하는 일이 많다.

### 세 프롬프트 비교

| 이름 | 지시 |
|---|---|
| 결론먼저 | 첫 문장에 결론, 그다음 설명 (261007 아침에 배포한 것) |
| 되묻기 | 결론먼저 + "상황이 빠져 답이 갈리면 되물어라" (지금 `lib/llm.ts`) |
| 근거먼저 | 되묻기 + "근거(조항 문장 그대로) → 적용 → 결론" 순서 강제 |

| 셋 다 답한 37문항 | 결론먼저 | 되묻기 | 근거먼저 |
|---|---|---|---|
| 필요한 내용을 전부 말함 | 26 | 25 | 29 |
| 채점 항목 | 69/85 | 69/85 | 75/85 |
| 애매한 질문에 되물음 | 0 | 0 | 0 |
| 첫 글자까지 평균 | 2.7초 | 3.1초 | 3.2초 |

| 끝내기 질문 8번씩 | 결론먼저 | 되묻기 | 근거먼저 |
|---|---|---|---|
| 긴 질문 | 6/8 | 5/8 | 3/8 |
| 짧은 질문 (사용자가 다시 물은 것) | 0/8 | 0/8 | 2/8 |

근거먼저는 전체에서 3문항 더 맞혔지만 끝내기 긴 질문에서는 6/8 -> 3/8로 떨어졌다.
확실히 낫다고 할 수 없어 넣지 않았다(`eval-answer`의 `근거먼저` 프리셋으로 남겨둠).
짧은 끝내기 질문은 정답 조항이 검색 6등·9등이라 셋 다 거의 못 맞힌다.

`eval-answer`에 `--only <질문 일부> --repeat <횟수>`를 더했다. 같은 질문을 여러 번 물어
몇 번 중 몇 번 맞는지 볼 때 쓴다.

### 결정: 프롬프트 문구 다듬기는 멈춘다 (261007)

세 프롬프트의 차이는 측정 편차 안이다. 전체 26/25/29는 같은 프롬프트를 두 번 재도 이만큼
갈리고, 끝내기 질문에서는 순위가 뒤집혔고(6/5/3), 되묻기는 셋 다 0번이었다.
**gpt-oss-20b는 지시문 문구를 바꿔서는 거의 달라지지 않는다.** 그래서 문구를 더 바꿔가며
재는 일(풀이 예시 넣기 포함)은 하지 않는다.

실제로 답을 바꾼 건 문구가 아니라 **모델이 보는 내용**이었다.

- 정답 조항을 검색 상위로 올린 것 (라인드라이브 16등 -> 4등, `docs/search.md`)
- 조항에 사람 말 설명을 붙여 AI에게도 준 것 ("찾지 못했습니다" 5/5 -> 5.09⒝⑸를 근거로 5/5)

남은 실패도 대부분 이쪽이다. 짧은 끝내기 질문은 정답 조항이 6등·9등, 애매한 질문 하나는
10등이라 모델이 정답 조항을 못 보거나, 넘긴 8개 중 엉뚱한 조항(9.05 안타, 9.15 기록)을 집는다.
**다음은 검색 쪽이다.** 틀린 질문마다 정답 조항이 왜 밀렸는지 보고, 모델에게 넘기는 조항이
덜 헷갈리게 만든다.

지금 `lib/llm.ts`의 프롬프트는 "되묻기"(결론먼저 + 되묻기 지시)다. 효과는 없지만 해도 없어서
되물음 상자가 쓰일 여지로 남겨뒀다. 바꿀 이유가 생기기 전까지 그대로 둔다.

## 6. 측정할 때 주의

- `eval-answer`는 앱과 같은 기준(첫 글자 20초, 멈춤 3초, SDK 재시도 3번)으로 끊는다.
  조각 사이 최대 공백도 기록한다. 멈춤 기준이 너무 짧은지 볼 수 있다.
- 앱의 라우트 재시도(빈 답일 때 다시 부르기)는 흉내 내지 않는다. 빈 답이 몇 번 나오는지도
  재야 할 값이라서다.
- 무료 API는 시간대에 따라 과부하 비율이 크게 달라진다. 같은 설정을 두 번 재면 에러가
  3개와 7개로 갈리기도 했다. 에러 난 문항은 채점에서 빠지므로 비교할 때는 **양쪽 다 답이
  나온 문항끼리** 비교한다.
- Windows에서 한글 경로(`정리`)가 들어가면 `new URL(...).pathname`이 `%EC...`로 남아
  파일을 못 찾는다. `fileURLToPath`를 쓴다. (`eval-answer.mjs`는 고쳤고
  `build-vectors.mjs`에는 아직 남아 있다)
