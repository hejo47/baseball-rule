# 검색 방식 기록

이 문서는 **2026-09-11 기준** 검색이 어떻게 동작하는지, 어떤 한계가 있는지,
무엇을 시도해봤고 무엇이 실패했는지를 남긴 기록이다.
검색 방식을 바꾸기 전에 읽고, 바꾼 뒤에는 이 문서를 갱신한다.

기준 커밋: `f186fa5` (규칙집에 없는 말을 규칙집 표현으로 바꿔 검색)
관련 코드: `lib/search.ts`, `data/rules.json`, `data/synonyms.json`

---

## 1. 데이터

`build_rules.py`가 2026 KBO 공식 야구규칙 PDF를 조각내 `data/rules.json`을 만든다.

| 항목 | 값 |
|---|---|
| 전체 조각 | 251개 |
| 규칙 조항 | 169개 |
| 용어의 정의 | 82개 |
| 본문 평균 길이 | 617자 (최대 4,248자) |
| 제목 길이 | 최소 1자, 중간값 8자, 최대 23자 |

2,500자가 넘는 조항은 하위 항목(⒜⒝⒞ → ⑴⑵⑶) 단위로 더 쪼갠다.
쪼갠 조각은 **원래 조항의 제목을 그대로 물려받는다.** 이게 뒤의 한계 3의 원인이다.

## 2. 검색이 도는 순서

서버가 뜰 때 색인을 한 번 만들어 메모리에 올려둔다. 이후 질문마다 251개 전부와
점수를 매겨 정렬한다. 외부 호출도 DB도 없다.

| 단계 | 시간 |
|---|---|
| 색인 만들기 (서버 시작 시 1회) | 약 40ms |
| 질문 하나 처리 | 0.18ms |

### 2-1. 글자를 두 개씩 겹쳐가며 자른다 (문자 바이그램)

한국어는 띄어쓰기로 단어를 자르기 어려워 단어 대신 글자 두 개씩 자른다.

```
"인필드플라이" -> 인필 / 필드 / 드플 / 플라 / 라이
```

질문과 조항을 같은 방식으로 자르고, 겹치는 조각이 많으면 비슷하다고 본다.

### 2-2. 흔한 조각은 깎고 드문 조각은 키운다 (TF-IDF)

각 조각이 251개 문서 중 몇 개에 나오는지 세어, 여기저기 나오는 조각(`경우`, `하는`)은
가중치를 낮추고 몇 군데만 나오는 조각(`보크`, `폭투`)은 높인다.

### 2-3. 제목과 본문을 따로 채점해 합친다

```
최종 점수 = 제목 유사도 x 0.85 + 본문 유사도 x 0.15
```

제목과 본문을 각각 별도의 벡터 공간으로 색인한다. 그래야 제목 안에서만 흔한 글자 조합이
본문 통계에 묻히지 않는다. 유사도는 코사인 유사도를 쓴다.

제목 색인에는 **제목과 영문명이 한 덩어리로** 들어간다. 예를 들어 `정의-54`는 `"아웃 OUT"`.
(한계 4의 원인)

### 2-4. 사전에 걸리면 질문을 하나 더 만들어 돌린다

`data/synonyms.json`에 사람들이 쓰는 말과 규칙집 표현의 대응을 적어둔다.

질문에 들어있는 말이 **규칙집 3개 조항 미만에서만 나오면**(`RARE_MAX_DOCS = 2`)
사람들만 쓰는 은어로 보고, 규칙집 표현을 덧붙인 질문을 하나 더 만든다.
두 질문을 각각 채점한 뒤 조항마다 **더 높은 쪽 점수**를 쓴다.

원래 질문 뒤에 확장어를 그냥 붙이지 않는 이유는, 확장어가 원래 질문의 비중을 깎아
이미 잘 찾던 질문까지 밀려나기 때문이다. (`주루방해` 6등 -> 16등)

## 3. 현재 성능 (2026-09-11)

채점 대상은 `data/testset.json`의 27문항. 그중 1개는 규칙집에 답이 없는 함정 문제다.

### 검색 순위 — `npm run eval:search`

| 지표 | 값 |
|---|---|
| 1등으로 찾음 | 20/26 (77%) |
| 상위 8개 안에 들어옴 | 24/26 (92%) |
| 아예 못 찾음 | 0 |

상위 8개가 중요한 이유는 그만큼만 AI에게 넘기기 때문이다. (`lib/llm.ts`의 `CONTEXT_LIMIT`)

못 찾는 2문항:

- `몸에 맞는 공이면 어떻게 돼?` — 10등. 정답 `5.06⒞`의 제목이 `"주루"`라 질문과 글자가 안 겹친다.
- `아웃이란 뭐야?` — 23등. 제목이 `"아웃"`인 조각 22개에 밀린다.

### 답변 정확도 — `npm run eval:answer`

AI 답변 끝의 인용 조항 번호를 정답과 대조해 채점한다.

| 지표 | 값 |
|---|---|
| 맞힘 | 23/27 (85%) |
| 틀림 - 검색이 정답을 안 넘겨줌 | 2 |
| 틀림 - 넘겨줬는데 AI가 못 씀 | 2 |
| 없는 조항 번호를 지어냄 | 1 |
| 평균 응답 시간 | 7.2초 (첫 글자 2.0초) |

## 4. 알려진 한계

### 한계 1. 글자가 안 겹치면 못 찾는다

뜻은 전혀 모르고 글자만 본다. `낫아웃`과 `제3스트라이크`는 겹치는 글자가 없어 영원히 0점이다.

`data/synonyms.json`이 이 구멍을 메우지만, **사람이 미리 적어둔 말만 커버된다.**
앞으로 들어올 질문을 다 예상해 적어둘 수는 없다. 이게 구조적으로 가장 큰 한계다.

### 한계 2. 제목 가중치 0.85가 너무 세다

답이 본문에만 있으면 사실상 못 찾는다.

`몸에 맞는 공`의 정답 `5.06⒞`는 제목이 `"주루"`다. 본문에 "타자의 몸 또는 옷에 닿았을 경우"가
정확히 있는데도 0.15만 반영돼 10등에 머문다.

실험: 제목 가중치를 0.55로 낮추면 1등 정확도가 20/26 -> 22/26으로 오른다.

### 한계 3. 제목이 조각마다 복제돼 있다

251조각인데 **서로 다른 제목은 145개뿐이다. 121조각이 제목을 공유한다.**

```
22조각  "아웃"
12조각  "공식기록지"
11조각  "선수교체 및 마운드 방문"
11조각  "자책점(EARNED RUN 自責點)"
10조각  "방해, 업스트럭션"
```

제목이 점수의 85%를 차지하므로 같은 제목 조각들이 통째로 같은 점수대에 몰린다.
`아웃이란 뭐야?`에서는 상위 21개가 전부 0.860~0.872에 붙어 있어, 다른 조항이 끼어들 틈이 없다.

**검색만의 문제가 아니라 `build_rules.py`가 조각을 만드는 방식의 문제이기도 하다.**

### 한계 4. 제목이 짧을수록 유리하다

코사인 유사도는 벡터 길이로 나누므로 제목이 짧으면 점수가 1에 가깝게 붙는다.

`아웃이란 뭐야?` 질문에 대해:

| 조항 | 색인된 제목 | 점수 |
|---|---|---|
| 5.09 조각들 | `아웃` | 0.860 ~ 0.872 |
| 정의-54 (진짜 정의) | `아웃 OUT` | **0.287** |
| 9.18 | `셧아웃` | 0.374 |

영문명 네 글자가 붙었다고 점수가 3분의 1로 깎여, 정의를 묻는 질문에서 진짜 정의가
`셧아웃`한테까지 진다.

### 한계 5. 점수에 절대 기준이 없다

0.011도 1등이고 0.87도 1등이다. 잘 찾았는지를 점수로 판단할 수 없다.

이 때문에 검색이 실패해도 8개를 꽉 채워 AI에게 넘기고, AI는 검색이 실패한 줄 모른 채
받은 조항으로 답을 만든다. `lib/llm.ts` 프롬프트에 "추측하지 말고 찾지 못했다고 답하라"가
이미 있지만, AI 입장에서는 자료를 받았으므로 발동하지 않는다.

실제 사례 — `몸에 맞는 공이면 어떻게 돼?` (1등 점수 0.011):

> "몸에 맞는 공은 파울 볼로 판정됩니다"

완전히 틀린 답이다. **검색 실패가 곧바로 그럴듯한 거짓말로 이어진다.**

## 5. 시도했다가 채택하지 않은 것

같은 실험을 반복하지 않기 위해 남긴다. 전부 `data/testset.json` 26문항으로 측정했다.

### 같은 조항에서 최대 N개만 남기기 — 실패

`아웃이란`이 한 조항에 점령당하는 걸 막으려 했다. 고치는 만큼 망가뜨렸다.

| 질문 | 지금 | 최대 2개 |
|---|---|---|
| 아웃이란 뭐야? | 23등 | 4등 |
| 자책점은 어떻게 계산해? | 4등 | **28등** |

`자책점`은 질문 자체가 `9.16` 한 조항에 대한 것이라, 형제 조각을 잘라내면 정답도 같이 잘린다.
총점은 24/26 그대로였다.

### 사전에 규칙집 문장을 그대로 넣기 — 실패

`몸에 맞는 공`에 대해 확장어 길이를 바꿔가며 측정했다.

| 사전에 넣은 확장어 | 순위 |
|---|---|
| (사전에 없음) | 10등 |
| `"투구가 타자의 몸 또는 옷에 닿았을 경우"` | **36등** |
| `"타자의 몸 또는 옷에 닿았을"` | 30등 |
| `"몸 또는 옷에 닿았을"` | 9등 |
| `"옷에 닿았을"` | **5등** |

긴 문장을 넣으면 `투구`, `타자`, `경우` 같은 흔한 조각이 딸려 들어가 엉뚱한 조항을 끌어올린다.

**확장어는 짧고, 그 조항에만 나오는 표현이어야 한다.**
기존 항목(`제3스트라이크`, `일시정지 경기`, `고의4구`)이 잘 듣는 이유도 같다.

### AI에게 넘기는 조항 개수 조절 — 8개가 적절

| 넘긴 조항 | 답변 정확도 | 평균 시간 | 없는 조항 지어냄 |
|---|---|---|---|
| 4개 | 20/27 (74%) | 5.7초 | 2건 |
| **8개** | **23/27 (85%)** | 7.2초 | 1건 |
| 16개 | 21/26 (81%) | 6.8초 | 3건 |

16개 측정만 분모가 26인 것은 `병살이 뭐야?`가 무료 API의 502로 실패했기 때문이다.
실험 조건과는 무관하다.

늘리면 오히려 떨어진다. 비슷한 조항이 많아질수록 AI가 헷갈려 없는 번호를 더 지어낸다.

참고로 **프롬프트 크기와 응답 속도는 거의 무관했다.** 8,203토큰을 넘긴 질문(9.3초)이
689토큰짜리(6.5초)보다 느리지 않았다. 병목은 프롬프트를 읽는 쪽이 아니라 답을 쓰는 쪽이다.

### 점수가 낮으면 아예 안 넘기기 — 보류

한계 5를 막으려 했으나 경계가 깨끗하게 갈리지 않는다.

- `몸에 맞는 공`도 1등 점수가 0.011이라 **답이 있는 질문까지 잘려나간다.**
- `FA 자격 요건이 뭐야?`는 규칙집에 답이 없는데 0.29로 높게 나와 걸러지지 않는다.

### 모호한 질문을 검색 단계에서 알아채기 — 실패

`아웃이란 뭐야?`처럼 막연한 질문이면 되묻게 하려 했다.
핵심어가 제목에 몇 개 조항이나 걸리는지로 재봤는데 갈리지 않았다.

| 질문 | 걸리는 조항 수 | 실제 |
|---|---|---|
| 아웃이란 뭐야? | 29개 | 23등, 모호함 |
| 낫아웃이 성립하는 경우는? | 29개 | **1등, 멀쩡함** |

`마운드 방문`(11개), `몰수경기`(17개), `자책점`(11개)도 같이 잡혔지만 전부 잘 답하는 질문이다.
단순히 세는 방식으로는 "진짜 모호한 것"과 "흔한 단어를 쓸 뿐인 것"이 구분되지 않는다.

## 6. 다음 후보 (2026-09-11 시점)

### A. 지금 구조 다듬기

제목 가중치 낮추기 + 영문명을 제목에서 떼어 따로 색인 + 상위 6자리는 점수 순 그대로 두고
남은 2자리만 아직 안 나온 조항에 주기.

측정 결과 상위 8개 안 24/26 -> **26/26**, 1등 20/26 -> **22/26**, 속도는 0.18ms 그대로.
한계 1은 그대로 남는다.

### B. 뜻으로 찾기 (임베딩)

한계 1, 4, 5가 한꺼번에 풀린다. 점수에 의미가 생겨 "못 찾았다" 판단도 가능해진다.

지금 쓰는 NVIDIA 무료 API에 임베딩 모델이 7개 있어 추가 비용은 없다.
(`nvidia/nv-embedqa-mistral-7b-v2`, `snowflake/arctic-embed-l` 등)

251조각은 미리 계산해두면 되지만 질문은 매번 API를 한 번 더 타야 한다.
0.18ms가 수백 ms가 된다. 답변이 7초 걸리는 것에 비하면 감당할 수 있을지 측정이 필요하다.

### C. 둘 다 쓰기 (하이브리드)

글자 점수와 의미 점수를 합친다. 정확한 용어는 글자가, 은어는 의미가 잡는다.
대신 섞는 비율을 또 튜닝해야 한다.

### 그 밖에

- AI에게 "상황에 따라 답이 갈리면 먼저 되물어라"를 지시문에 넣기 (비용 없음, 채점기로 검증 가능)
- `build_rules.py`에서 쪼갠 조각의 제목에 상위 맥락을 붙여 한계 3을 데이터 쪽에서 완화
