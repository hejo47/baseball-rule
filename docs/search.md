# 검색 방식 기록

이 문서는 검색이 어떻게 동작하는지, 어떤 한계가 있는지, 무엇을 시도했고
무엇이 실패했는지를 남긴 기록이다.
검색 방식을 바꾸기 전에 읽고, 바꾼 뒤에는 이 문서를 갱신한다.

| | |
|---|---|
| 마지막 갱신 | 2026-09-12 |
| 관련 코드 | `lib/search.ts`, `lib/embedding.ts`, `scripts/build-vectors.mjs` |
| 관련 데이터 | `data/rules.json`, `data/synonyms.json`, `data/vectors.json`, `data/testset.json` |

---

## 1. 데이터

문서 두 개를 한 묶음으로 검색한다. 다루는 범위가 겹치지 않는다.

| 문서 | 만드는 스크립트 | 파일 | 조각 |
|---|---|---|---|
| 2026 KBO 공식 야구규칙 | `build_rules.py` | `data/rules.json` | 304개 |
| 2026 KBO 리그 규정 | `build_league.py` | `data/league.json` | 153개 |
| | | 합계 | **457개** |

야구규칙에는 비디오 판독, 피치클락, ABS, 엔트리 같은 운영 규정이 아예 없다.
그런 질문은 리그 규정 쪽에 답이 있다.

### 야구규칙 (`build_rules.py`)

조항 222조각 + 용어의 정의 82조각. 본문 평균 550자, 최장 4,244자.
2,500자가 넘는 조항은 하위 항목(⒜⒝⒞ → ⑴⑵⑶) 단위로 더 쪼갠다.
쪼갠 조각은 원래 조항의 제목을 그대로 물려받는다. (한계 2의 원인)

어떤 번호가 조항인지는 **목차가 정한다.** 목차 76개를 전부 찾지 못하면 경고를 찍는다.

### 리그 규정 (`build_league.py`)

제1조~제78조와 부록 8개. 조 번호가 1부터 끝까지 중복 없이 이어져서,
번호가 순서대로 늘어나는 줄만 조항 시작으로 인정한다. 본문 속 상호참조는 걸러진다.

부록은 목차에 `■ 제목`으로 나온다. 고척스카이돔 그라운드룰, ABS 규정,
경기의 스피드업, KBO 피치클락 규정, 기록 이의신청 심의 제도, 경기 중 선수단 행동
관련 지침, 벌칙내규, KBO 표창규정. 부록에는 조 번호가 없어서 잘라주지 않으면
마지막 조항(제78조)이 문서 끝까지 빨아들여 3만 자짜리 덩어리가 된다.

목차의 부록 9개 중 8개를 찾는다. 못 찾는 하나는 `2026년 구단별 경기관리인...`으로,
목차에서 제목이 두 줄로 나뉘어 있다. 담당자 명단 표라 검색 가치가 낮아 두었다.

### 뜻 벡터 (`scripts/build-vectors.mjs`)

두 파일을 이어 붙인 순서 그대로 457개 × 2048차원, 6.6MB.
**저장소에 커밋한다.** 규정은 1년에 한 번 바뀌는 데이터라 배포마다 457번씩 API를
다시 탈 이유가 없고, 그때 무료 API가 죽어 있으면 배포가 실패한다.

규정을 바꿨으면 `npm run build:vectors`를 다시 돌린다.
개수가 어긋나면 `lib/search.ts`가 뜨면서 에러를 낸다.

## 2. 검색이 도는 순서

글자가 얼마나 겹치는지(**글자 점수**)와 뜻이 얼마나 가까운지(**뜻 점수**)를
따로 매긴 뒤 반반 섞는다.

| 단계 | 시간 |
|---|---|
| 색인 만들기 (서버 시작 시 1회) | 약 40ms |
| 글자 점수 매기기 | 0.18ms |
| 질문을 뜻 벡터로 바꾸기 (API 호출) | 중간값 326ms |

### 2-1. 글자 점수

**글자를 두 개씩 겹쳐가며 자른다 (문자 바이그램).**
한국어는 띄어쓰기로 단어를 자르기 어려워 단어 대신 글자 두 개씩 자른다.

```
"인필드플라이" -> 인필 / 필드 / 드플 / 플라 / 라이
```

**흔한 조각은 깎고 드문 조각은 키운다 (TF-IDF).**
여기저기 나오는 `경우`, `하는`은 가중치를 낮추고 `보크`, `폭투`는 높인다.

**제목·영문명·본문을 따로 색인해 합친다.**

```
글자 점수 = max(제목 유사도, 영문명 유사도) x 0.55 + 본문 유사도 x 0.45
```

제목과 영문명을 `"아웃 OUT"`처럼 한 덩어리로 색인하면 안 쓰는 쪽이 벡터 길이만 늘려
점수를 깎아먹는다. 따로 색인해 **둘 중 높은 쪽**을 쓰면 한글로 물어도 영어로 물어도 손해가 없다.

**사전에 걸리면 질문을 하나 더 만들어 돌린다.**
`data/synonyms.json`에 사람들이 쓰는 말과 규칙집 표현의 대응을 적어둔다.
질문에 들어있는 말이 규칙집 3개 조항 미만에서만 나오면(`RARE_MAX_DOCS = 2`) 은어로 보고,
규칙집 표현을 덧붙인 질문을 하나 더 만들어 채점한 뒤 조항마다 더 높은 쪽을 쓴다.

원래 질문 뒤에 확장어를 그냥 붙이지 않는 이유는, 확장어가 원래 질문의 비중을 깎아
이미 잘 찾던 질문까지 밀려나기 때문이다. (`주루방해` 6등 -> 16등)

### 2-2. 뜻 점수

`data/vectors.json`에 미리 만들어둔 조각 벡터와, 그때그때 API로 만든 질문 벡터의
코사인 유사도. 벡터를 저장할 때 길이를 1로 맞춰놔서 계산은 내적 한 번이면 끝난다.

**API가 실패하면 글자 점수만으로 답한다.** 무료 API는 502를 심심찮게 내는데,
그때 검색 전체가 죽는 대신 조금 덜 정확해지는 쪽을 택했다. (`lib/embedding.ts`)

### 2-3. 둘을 섞는다

두 점수는 눈금이 다르다. 글자 점수는 0.05~0.87, 뜻 점수는 0.07~0.58로 나온다.
그냥 더하면 글자 쪽이 일방적으로 이기므로, 각자 **그 질문에서의 최댓값으로 나눠
0~1로 맞춘 뒤** 반반 섞는다.

결과는 상위 30개(`RESULT_LIMIT`)까지만 돌려준다. 뜻 점수는 아무 조항에나 0보다 큰 값을
주기 때문에 그냥 두면 251개가 전부 딸려와 응답이 400KB가 된다.
AI가 보는 건 상위 8개(`lib/llm.ts`의 `CONTEXT_LIMIT`)뿐이다.

## 3. 현재 성능

채점 대상은 `data/testset.json`의 30문항. 그중 1개는 두 문서 어디에도 답이 없는 함정이다.

### 검색 순위 — `npm run eval:search`

| 지표 | 글자만 (260907) | 하이브리드 (260912) | 리그 규정 추가 (260912) |
|---|---|---|---|
| 채점 대상 | 26문제 | 26문제 | 29문제 |
| 1등으로 찾음 | 20/26 (77%) | 23/26 (88%) | 23/29 (79%) |
| 상위 8개 안 | 24/26 (92%) | 26/26 (100%) | 28/29 (97%) |
| 아예 못 찾음 | 0 | 0 | 0 |

새로 넣은 리그 규정 문항 3개는 전부 상위 8개 안에 들어온다.
(`비디오 판독 신청` 1등, `판독 횟수` 2등, `피치클락` 4등)

### 답변 정확도 — `npm run eval:answer`

**조항 번호를 맞혔는지가 아니라, 답에 들어가야 할 내용이 들어갔는지를 본다.**
질문마다 `data/testset.json`의 `must`에 필수 내용을 적어두고 대조한다. 30문항에 79개 항목.

```json
{
  "q": "낫아웃이 성립하는 경우는?",
  "must": [
    { "name": "제3스트라이크", "any": ["제3스트라이크", "3스트라이크", "삼진"] },
    { "name": "포수가 잡지 못함", "any": ["잡지 못", "놓치", "포구하지 못"] }
  ]
}
```

| 지표 | 값 (260912) |
|---|---|
| 필요한 내용을 전부 말함 | 25/30 (83%) |
| 항목 단위 적중 | 70/79 (89%) |
| 틀림 - 검색이 근거를 안 넘겨줌 | **0** |
| 틀림 - 넘겨줬는데 모델이 못 씀 | 5 |
| 없는 조항 번호를 지어냄 | **0** |
| 함정에 답을 지어냄 | **0** |
| 모델 호출 평균 시간 | 5.6초 |

주의: `eval:answer`의 시간은 모델 호출만 잰 것이라 질문 임베딩 326ms가 빠져 있다.

남은 실패는 **전부 모델 쪽이다.** 필요한 내용이 넘겨준 조항 안에 있었는데 못 썼다.

- `낫아웃이 성립하는 경우는?` — 제3스트라이크를 제대로 다루지 못한다.
- `몸에 맞는 공이면 어떻게 돼?` — 근거를 받고도 "찾지 못했다"고 하거나 틀린 답을 낸다.
- `인필드 플라이는 언제 선언돼?` — 선언 시점은 맞게 말하나 성립 조건을 빠뜨린다.
- `세트 포지션이 뭐야?` — 자세 설명은 정확하다. "두 가지 정규투구자세 중 하나"라는
  맥락만 빠졌다. 채점이 빡빡한 쪽이지만 기준을 결과에 맞춰 무르게 고치지 않으려고 그대로 뒀다.
- `피치클락은 몇 초야?` — 23초와 18초는 말하나 타석간 33초를 빠뜨린다.

## 4. 알려진 한계

### 한계 1. 사전은 사람이 적어둔 말만 커버한다

뜻 검색이 들어오면서 많이 완화됐다. `아웃이란 뭐야?`는 글자로는 23등이었는데
뜻으로는 1등이다. 하지만 반대 방향도 있다. `낫아웃`은 뜻으로만 찾으면 20등까지 밀리고
사전(글자 쪽)이 잡아줘야 1등이 된다.

**둘 중 하나만으로는 안 되고, 사전은 여전히 필요하다.**

### 한계 2. 제목이 조각마다 복제돼 있다

251조각인데 **서로 다른 제목은 145개뿐이다. 121조각이 제목을 공유한다.**

```
22조각  "아웃"
12조각  "공식기록지"
11조각  "선수교체 및 마운드 방문"
11조각  "자책점(EARNED RUN 自責點)"
10조각  "방해, 업스트럭션"
```

한 조항이 상위권을 독점하는 원인이다. 뜻 점수가 섞이면서 증상은 줄었지만
원인은 그대로다. **검색이 아니라 `build_rules.py`가 조각을 만드는 방식의 문제다.**

### 한계 3. 문서를 추가하면 사전 항목이 조용히 꺼질 수 있다

확장은 '규칙집이 거의 쓰지 않는 말'에만 걸린다(`RARE_MAX_DOCS = 2`). 그래서 문서를
새로 넣으면 그 말이 흔해져 항목이 저절로 멈춘다.

리그 규정을 넣자 `비디오 판독 대상 플레이` 목록에 "⑤ 몸에 맞는 공"이 글자 그대로
들어 있어서, "몸에 맞는 공"이 2개 조항에서 나오게 됐다. 경계선이라 아직 작동하지만
하나만 더 늘면 꺼진다.

`lib/search.ts`가 색인을 만들 때 확인해서 꺼진 항목이 있으면 로그로 알린다.

### 한계 4. 점수에 절대 기준이 없다

**"검색이 실패했다"를 점수로 판단할 수 없다.** 문턱을 세울 자리가 없다.

| | 답 있는 질문의 최저점 | 답 없는 질문의 최고점 |
|---|---|---|
| 글자 점수 | 0.050 | 0.242 (순서가 뒤집힘) |
| 뜻 점수 | 0.168 (`병살이 뭐야?`) | 0.188 (`FA 자격 요건이 뭐야?`) |

뜻 점수는 적어도 순서는 맞지만 0.168과 0.188 사이에 선을 긋는 건 너무 아슬아슬하다.
(다만 `FA 자격 요건`은 야구규약 PDF에 답이 있는 질문이라 진짜 함정은 아니다.)

이 때문에 검색이 실패해도 8개를 꽉 채워 AI에게 넘기고, AI는 실패한 줄 모른 채
받은 조항으로 답을 만든다. `lib/llm.ts` 프롬프트에 "추측하지 말고 찾지 못했다고 답하라"가
이미 있지만, AI 입장에서는 자료를 받았으므로 발동하지 않는다.

### 한계 5. 긴 조각은 앞부분만 벡터로 만든다

조각 하나가 최대 4,248자인데 임베딩 모델의 입력 길이에 한도가 있어
앞 1,200자만 쓴다(`scripts/build-vectors.mjs`의 `MAX_CHARS`).
뒷부분에만 답이 있는 조항은 뜻 검색으로 못 찾는다. 글자 검색이 그걸 메운다.

### 한계 6. 쓸 수 있는 임베딩 모델이 하나뿐이다

NVIDIA 목록에는 임베딩 모델이 7개 있지만 이 계정에서 6개는 404가 난다.
`nvidia/nemotron-3-embed-1b` 하나만 열려 있다.

## 5. 시도했다가 채택하지 않은 것

같은 실험을 반복하지 않기 위해 남긴다. 전부 `data/testset.json` 26문항으로 측정했다.

### 영문명을 제목에서 떼어내 따로 색인하기 — 실패

한계 2를 풀려고 영문명을 별도 공간에 낮은 가중치(0.1)로 뒀더니
**영어로 물었을 때가 다 깨졌다.**

| 질문 | 한 덩어리 | 떼어냄 |
|---|---|---|
| `infield fly` | 정의-40 ✅ | 9.04 타점 ❌ |
| `balk` | 정의-3 ✅ | 9.07⒣ 도루 ❌ |
| `wild pitch` | 정의-81 ✅ | 9.05 안타 ❌ |

**떼는 게 아니라 둘 중 높은 쪽을 쓰는 방식으로 바꿔야 한다.** 그러면 영어 질문의
점수가 0.53~0.63에서 0.85~0.89로 오히려 올라간다. 지금은 이쪽을 쓰고 있다.

### 같은 조항에서 최대 N개만 남기기 — 실패

한 조항이 상위 8칸을 점령하는 걸 막으려 했다. 고치는 만큼 망가뜨렸다.

| 질문 | 그냥 | 최대 2개 |
|---|---|---|
| 아웃이란 뭐야? | 23등 | 4등 |
| 자책점은 어떻게 계산해? | 4등 | **28등** |

`자책점`은 질문 자체가 `9.16` 한 조항에 대한 것이라 형제 조각을 자르면 정답도 같이 잘린다.

### 상위 6자리 뒤 2자리를 다른 조항에 주기 (다양성) — 하이브리드에서는 불필요

캡의 대안으로 만들었고 **글자 검색만 쓸 때는 잘 들었다.**
`아웃이란` 23등 -> 7등, `자책점`은 4등 유지, 상위 8개 안 24/26 -> 26/26.

그런데 **뜻 점수를 섞으면 오히려 해롭다.** 임베딩이 이미 다른 조항을 끌어올려 주기 때문에,
거기에 다양성까지 얹으면 `자책점`이 4등 -> 9등으로 밀린다.
그래서 하이브리드에는 넣지 않았다.

### 사전에 규칙집 문장을 그대로 넣기 — 실패

`몸에 맞는 공`에 대해 확장어 길이를 바꿔가며 측정했다.

| 사전에 넣은 확장어 | 순위 |
|---|---|
| (사전에 없음) | 10등 |
| `"투구가 타자의 몸 또는 옷에 닿았을 경우"` | **36등** |
| `"타자의 몸 또는 옷에 닿았을"` | 30등 |
| `"몸 또는 옷에 닿았을"` | 9등 |
| `"옷에 닿았을"` | **5등** |

긴 문장은 `투구`, `타자`, `경우` 같은 흔한 조각을 끌고 들어와 엉뚱한 조항을 올린다.
**확장어는 짧고, 그 조항에만 나오는 표현이어야 한다.**
기존 항목(`제3스트라이크`, `일시정지 경기`, `고의4구`)이 잘 듣는 이유도 같다.

### 뜻 검색만 쓰기 — 실패

1등은 가장 잘 맞히지만(23/26) **상위 8개 안은 오히려 나빠진다(23/26).**
`낫아웃` 20등, `몸에 맞는 공` 15등. 맞힐 땐 확실히 1등으로 가져오는데 놓칠 땐 크게 놓친다.

### AI에게 넘기는 조항 개수 조절 — 8개가 적절

| 넘긴 조항 | 답변 정확도 | 평균 시간 | 없는 조항 지어냄 |
|---|---|---|---|
| 4개 | 20/27 (74%) | 5.7초 | 2건 |
| **8개** | **23/27 (85%)** | 7.2초 | 1건 |
| 16개 | 21/26 (81%) | 6.8초 | 3건 |

(글자 검색만 쓰던 260911 기준. 16개 측정만 분모가 26인 것은 `병살이 뭐야?`가
무료 API의 502로 실패했기 때문이며 실험 조건과는 무관하다.)

늘리면 오히려 떨어진다. 비슷한 조항이 많아질수록 AI가 헷갈려 없는 번호를 더 지어낸다.

참고로 **프롬프트 크기와 응답 속도는 거의 무관했다.** 8,203토큰을 넘긴 질문(9.3초)이
689토큰짜리(6.5초)보다 느리지 않았다. 병목은 프롬프트를 읽는 쪽이 아니라 답을 쓰는 쪽이다.

### 점수가 낮으면 아예 안 넘기기 — 보류

한계 4 참고. 글자 점수로도 뜻 점수로도 경계가 깨끗하게 갈리지 않는다.

### 답변을 인용 조항 번호로 채점하기 — 260912에 폐기

처음에는 답변 끝의 인용 번호를 `expect`와 대조해 채점했다. 파서를 고쳐 조항이
제대로 쪼개지자 이 방식이 무너졌다.

**정당한 정답이 여러 개가 됐다.** `세트 포지션이 뭐야?`의 `정의-70`은 내용이
"두 가지 정규투구자세 가운데 하나다"가 전부다. 모델이 실제 설명이 있는 `5.07⒜⑵`를
골랐는데 오답이 됐다. `자책점`은 `expect`가 `9.16⒝`(자책점이 되지 않는 예외)였는데
진짜 계산법인 `9.16⒜`는 그때 데이터에 없어서 그렇게 적혀 있던 것이었다.

**가짜 정답도 나왔다.** `낫아웃이 성립하는 경우는?`에 모델이 `5.05⒜⑴`을 인용해
"부분 정답" 처리됐는데, 답변 내용은 제3스트라이크를 한 번도 언급하지 않은 엉뚱한
글이었다. 번호만 그럴듯하면 통과하는 구멍이 있었다.

**필요한 내용이 조항 하나에 없는 경우도 있다.** `투수가 이물질을 바르면`은 금지
행위가 `6.02⒞`에, 벌칙(즉시 퇴장)이 `6.02⒟`에 나뉘어 있다.

인용 채점을 완전히 버리지는 않았다. "규칙집에 없는 번호를 댔는가"는 그대로 센다.
데이터에서 조항 11개가 빠진 걸 찾아낸 게 바로 이 숫자였다.

### 리그 규정을 넣은 대가 — 질문 하나가 밀렸다

조각이 304개에서 457개로 늘면서 `몸에 맞는 공이면 어떻게 돼?`가 7등 -> 9등으로
상위 8개 밖으로 밀렸다. 끼어든 것은 `리그-제28조-3 비디오 판독`인데, 비디오 판독
대상 플레이 목록에 "⑤ 몸에 맞는 공"이 글자 그대로 있어 **노이즈가 아니라 진짜 관련
조항이다.**

사전 확장어를 늘려 되돌리려 했으나 전부 더 나빠졌다. (9등 -> 14등, 19등)
짧은 확장어 하나가 최선이라는 앞의 결론이 다시 확인됐다.

### 모호한 질문을 검색 단계에서 알아채기 — 실패

`아웃이란 뭐야?`처럼 막연한 질문이면 사용자에게 되묻게 하려 했다.
핵심어가 제목에 몇 개 조항이나 걸리는지로 재봤는데 갈리지 않았다.

| 질문 | 걸리는 조항 수 | 실제 |
|---|---|---|
| 아웃이란 뭐야? | 29개 | 23등, 모호함 |
| 낫아웃이 성립하는 경우는? | 29개 | **1등, 멀쩡함** |

`마운드 방문`(11개), `몰수경기`(17개), `자책점`(11개)도 같이 잡혔지만 전부 잘 답하는 질문이다.
단순히 세는 방식으로는 "진짜 모호한 것"과 "흔한 단어를 쓸 뿐인 것"이 구분되지 않는다.

  `낫아웃`에 제3스트라이크와 무관한 설명을 내놓는다. 둘 다 근거는 제대로 넘어갔다.
