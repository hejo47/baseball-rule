# 검색 방식 기록

이 문서는 검색이 어떻게 동작하는지, 어떤 한계가 있는지, 무엇을 시도했고
무엇이 실패했는지를 남긴 기록이다.
검색 방식을 바꾸기 전에 읽고, 바꾼 뒤에는 이 문서를 갱신한다.

| | |
|---|---|
| 마지막 갱신 | 2026-10-23 |
| 관련 코드 | `build_rules.py`, `build_league.py`, `build_bylaws.py`, `lib/search.ts`, `lib/tokenizer.ts`, `lib/embedding.ts`, `scripts/build-tokens.mjs`, `scripts/build-vectors.mjs`, `scripts/build-plain-vectors.mjs` |
| 관련 데이터 | `data/rules.json`, `data/league.json`, `data/bylaws.json`, `data/synonyms.json`, `data/plain.json`, `data/tokens.json`, `data/vectors.json`, `data/plain-vectors.json`, `data/testset.json` |

답변 모델과 응답 처리(시간 제한, 재시도, 모델 교체)는 `docs/answer.md`에 따로 적는다.

## 1. 데이터

문서 세 개를 한 묶음으로 검색한다. 다루는 범위가 거의 겹치지 않는다.

| 문서 | 만드는 스크립트 | 파일 | 조각 |
|---|---|---|---|
| 2026 KBO 공식 야구규칙 | `build_rules.py` | `data/rules.json` | 304개 |
| 2026 KBO 리그 규정 | `build_league.py` | `data/league.json` | 153개 |
| 2026 KBO 규약 (261023 추가) | `build_bylaws.py` | `data/bylaws.json` | 454개 |
| | | 합계 | **911개** |

야구규칙에는 비디오 판독, 피치클락, ABS, 엔트리 같은 운영 규정이 아예 없다.
그런 질문은 리그 규정 쪽에 답이 있다. FA 자격, 선수 정원, 최저연봉, 외국인선수,
포스팅, 샐러리캡(경쟁균형세)처럼 선수 신분과 계약에 관한 질문은 규약에만 있다.

### 야구규칙 (`build_rules.py`)

조항 222조각 + 용어의 정의 82조각. 본문 평균 550자, 최장 4,244자.
2,500자가 넘는 조항은 하위 항목(⒜⒝⒞ → ⑴⑵⑶) 단위로 더 쪼갠다.
쪼갠 조각의 제목은 `조항 제목 · 자기 항목의 머리말`이다(예: `아웃 · 페어 플라이 볼, ...`). 한계 2 참고.

어떤 번호가 조항인지는 **목차가 정한다.** 목차 76개를 전부 찾지 못하면 경고를 찍는다.

### 리그 규정 (`build_league.py`)

제1조~제78조와 부록 8개. 조 번호가 1부터 끝까지 중복 없이 이어져서,
번호가 순서대로 늘어나는 줄만 조항 시작으로 인정한다. 본문 속 상호참조는 걸러진다.

부록은 목차에 `■ 제목`으로 나온다. 고척스카이돔 그라운드룰, ABS 규정,
경기의 스피드업, KBO 피치클락 규정, 기록 이의신청 심의 제도, 경기 중 선수단 행동
관련 지침, 벌칙내규, KBO 표창규정. 부록에는 조 번호가 없어서 잘라주지 않으면
마지막 조항(제78조)이 문서 끝까지 빨아들여 3만 자짜리 덩어리가 된다.

목차의 부록 9개 중 8개를 찾는다. 못 찾는 하나는 `2026년 구단별 경기관리인...`으로,
목차에서 제목이 두 줄로 나뉘어 있다. 담당자 명단 표라 검색 가치가 낮아 두었다.

### 규약 (`build_bylaws.py`)

268쪽 한 권에 문서 17개가 묶여 있다. KBO 규약(제1~188조, 199조각)이 중심이고,
정관, 선수·감독·외국인선수 계약서, 외국인선수 고용규정, 한·미/한·일/한·대만 선수계약협정,
아마 협정서, 국가대표팀 운영규정, 상벌위원회·경기사용구·배트·연금보험 규정이 함께 있다.
평균 286자, 최장 2,393자.

**이 PDF는 `pdftotext`로 뽑으면 한글이 전부 깨진다**('Adobe-Korea1' CMap을 못 찾는다).
그래서 스크립트가 PDF를 직접 받아 PyMuPDF로 읽는다(`pip install pymupdf`).

문서마다 조항 표기가 달라(`제1조 [목적]`, `제1조 (목적)`, `제1조 총재의...`, `1.`, `1)`, `제1장`)
문서별 쪽 범위와 자르는 방식을 스크립트 맨 위 `DOCUMENTS` 표에 적어 둔다.
id는 문서마다 앞머리를 달리 붙여 겹치지 않게 한다(`규약-제162조`, `정관-제9조`,
`외국인고용-제10조`, `한미협정-9`). 리그 규정처럼 **번호가 순서대로 늘어날 때만** 조항으로
인정한다. 그 위에 더 처리한 것:

- `제88조의 2`처럼 가지 번호가 붙는 조가 3개 있다. '의1' 없이 '의2'부터 시작한다.
- 본문 줄이 마침 `제4장의 선수 연봉은`으로 시작해 장 제목으로 잡힌 적이 있어, 장 번호도
  순서대로 늘어날 때만 인정한다.
- 부칙에서는 조 번호가 1부터 다시 시작한다. 부칙은 통째로 한 조각(`규약-부칙`)이다.

빼는 것: 한·미 협정의 영문 번역(215~225쪽), 한·일·한·대만 협정에서 한국어 본문 바로 뒤에
붙은 영문(`... AGREEMENT` 제목 줄에서 멈춘다), 글자가 없는 그림 쪽(외국인선수 계약서 영문,
부록 양식). 영문은 한국어와 내용이 같아 넣으면 같은 조항이 두 번 걸리기만 한다.

### 뜻 벡터 (`scripts/build-vectors.mjs`)

세 파일을 이어 붙인 순서 그대로 911개 × 2048차원, 13.2MB(규약을 넣기 전 457개, 6.6MB).
**저장소에 커밋한다.** 규정은 1년에 한 번 바뀌는 데이터라 배포마다 911번씩 API를
다시 탈 이유가 없고, 그때 무료 API가 죽어 있으면 배포가 실패한다.

규정을 바꿨으면 `npm run build:vectors`를 다시 돌린다.
개수가 어긋나면 `lib/search.ts`가 뜨면서 에러를 낸다.

### 사람 말 설명 (`data/plain.json`)

규칙집 문장을 사람들이 묻는 말투로 풀어 쓴 설명을 조항 번호에 붙여둔다.
사전(`synonyms.json`)이 **질문 쪽의 단어 하나**를 규칙집 말로 바꿔준다면,
이건 **조항 쪽에** 사람 말을 붙인다. 상황을 풀어 쓴 질문은 드문 단어가 없어
사전이 못 잡기 때문이다. (5절 "사전으로 상황 질문 잡기" 참고)

```json
{ "id": "5.09⒝⑸", "plain": "뜬공이나 라인드라이브(직선타, 라이너)가 땅에 닿기 전에 잡히면 ...", "note": "왜 붙였나" }
```

- 검색은 설명을 **본문 뒤에 붙여 글자 색인**하고, 설명 벡터도 따로 만들어 **원문 벡터와
  높은 쪽**을 쓴다.
- AI에게도 `(쉬운 설명, 규칙집 원문 아님: ...)`으로 같이 준다. 화면에는 원문만 나간다.
- 설명을 고치면 `npm run build:plain`으로 벡터를 다시 만든다(`data/plain-vectors.json`).
  몇 개뿐이라 몇 초면 끝나고, 911개 전체를 다시 만들 필요는 없다.
  설명과 벡터가 어긋나거나 없는 조항 번호를 적으면 `lib/search.ts`가 에러를 낸다.

지금은 2개(5.09⒝⑸ 귀루, 5.06⒞ 몸에 맞는 공)다. 설명이 틀리면 검색 순위와 AI 답 양쪽에 영향을 주므로
규칙집 원문과 맞는지 사람이 확인하고 넣는다.

## 2. 검색이 도는 순서

글자가 얼마나 겹치는지(**글자 점수**)와 뜻이 얼마나 가까운지(**뜻 점수**)를
따로 매긴 뒤 반반 섞는다. 261023부터는 이걸 **분야마다(경기 / 규약) 따로** 하고,
질문이 어느 분야에 가까운지에 따라 가중치를 준다(2-4).

| 단계 | 시간 |
|---|---|
| 색인 만들기 (서버 시작 시 1회) | 약 40ms |
| 글자 점수 매기기 | 0.18ms |
| 질문을 뜻 벡터로 바꾸기 (API 호출) | 중간값 326ms |

### 2-1. 글자 점수

**조항과 질문을 형태소로 자른다 (oktjs, `lib/tokenizer.ts`).**
조사·어미·기호는 버리고, 동사·형용사는 원형으로 바꾼다.

```
"몸 맞는 공이면 주자는 어떻게 돼?" -> 몸 / 맞다 / 공이 / 주자 / 어떻다 / 돼다
```

완벽하지는 않다. "공이면"을 공+이면으로 나누지 못하고 "돼"를 "돼다"로 만든다(Kiwi는 둘 다 맞게
자른다). 그래도 글자 두 개씩 자르던 때보다 검색이 나았다(5절).

조항 쪽은 `scripts/build-tokens.mjs`가 미리 잘라 `data/tokens.json`에 둔다(911개에 26초).
서버는 질문만 그때그때 자른다. 서버가 뜬 뒤 첫 검색은 oktjs를 불러오느라 2초쯤 더 걸린다.

**BM25로 매긴다.** 흔한 말(`경우`, `하다`)은 가중치가 낮고 드문 말(`보크`, `폭투`)은 높다.
긴 조항일수록 점수를 깎아, 여러 주제가 섞인 긴 조항이 아무 질문에나 걸리지 않게 한다.

**제목, 영문명, 본문(본문 + 사람 말 설명)을 따로 매겨 합친다.**

```
글자 점수 = max(제목 BM25, 영문명 BM25) x 0.55 + 본문 BM25 x 0.45   (각 칸은 그 질문의 최고점으로 나눔)
```

**숫자 바로 뒤에 붙은 명사는 한 낱말로 묶는다**("2루", "2아웃", "1사"). **질문에 "맞다"가 있으면 "닿다"도
찾는다**(규칙집은 둘 다 쓰고 사람은 "맞다"로만 묻는다). 이유는 5절.

**질문 쪽에서 묻는 말투 형태소를 버린다**(`QUESTION_WORDS`, 261023). 두 종류다.

| 종류 | 형태소 | 문제 |
|---|---|---|
| 조항에 거의 없는 말 | `돼다`(잘못 자른 "돼", 4개 조항), `몇`(1개), `얼마`(2개), `언제`(11개), `어떻다`(39개), `뭐`(0개) | BM25가 드문 말로 보고 큰 점수를 줘, 그 말이 우연히 든 조항을 끌어올린다 |
| 거의 모든 조항에 있는 말 | `하다`(850개), `되다`, `있다`, `수` | 점수는 작지만, 제목 칸은 그 질문의 최고점으로 나누므로 다른 말이 제목에 안 걸리면 제목에 `하다`가 든 조항이 제목 칸 1.0을 받는다 |

`승부조작하면 어떻게 돼?`(승부조작 / 하다 / 어떻다 / 돼다)에서 둘 다 터졌다. 규약 제148조(부정행위)에
"승부조작"이 세 번 나오는데, `돼다`가 든 규칙 조항과 제목에 `하다`가 든 규칙 조항에 밀려 상위 8개에
규약이 하나도 없었다. 뺀 뒤 1등. 시험 46문항은 1등 개수(29)와 상위 8개(46/46)가 같고,
4개가 오르고(라인드라이브 3->2, 그럼 2아웃이면 4->2, 짧은 끝내기 5->4, 낫삼진 상황 8->7)
2개가 내렸다(`낫아웃이 성립하는 경우는?` 3->5, `비디오 판독 몇 번까지` 3->4).

처음에는 글자를 두 개씩 겹쳐 잘라("인필드플라이" -> 인필 / 필드 / 드플 / ...) TF-IDF 코사인으로
매겼다. 261007에 바꿨다(5절 "글자 점수를 형태소 분석 + BM25로").

**사전에 걸리면 질문을 하나 더 만들어 돌린다.**
`data/synonyms.json`에 사람들이 쓰는 말과 규칙집 표현의 대응을 적어둔다.
질문에 들어있는 말이 규칙집 3개 조항 미만에서만 나오면(`RARE_MAX_DOCS = 2`) 은어로 보고,
규칙집 표현을 덧붙인 질문을 하나 더 만들어 채점한 뒤 조항마다 더 높은 쪽을 쓴다.

원래 질문 뒤에 확장어를 그냥 붙이지 않는 이유는, 확장어가 원래 질문의 비중을 깎아
이미 잘 찾던 질문까지 밀려나기 때문이다. (`주루방해` 6등 -> 16등)

**사람 말 설명이 있는 조항은 설명을 본문 뒤에 붙여 색인한다.**

### 2-2. 뜻 점수

`data/vectors.json`에 미리 만들어둔 조각 벡터와, 그때그때 API로 만든 질문 벡터의
코사인 유사도. 벡터를 저장할 때 길이를 1로 맞춰놔서 계산은 내적 한 번이면 끝난다.

사람 말 설명이 있는 조항은 원문 벡터와 설명 벡터(`data/plain-vectors.json`) 중
질문에 더 가까운 쪽을 쓴다.

**API가 실패하면 글자 점수만으로 답한다.** 무료 API는 502를 심심찮게 내는데,
그때 검색 전체가 죽는 대신 조금 덜 정확해지는 쪽을 택했다. (`lib/embedding.ts`)

### 2-3. 둘을 섞는다

두 점수는 눈금이 다르다. 글자 점수는 0.05~0.87, 뜻 점수는 0.07~0.58로 나온다.
그냥 더하면 글자 쪽이 일방적으로 이기므로, 각자 **그 질문에서의 최댓값으로 나눠
0~1로 맞춘 뒤** 반반 섞는다.

결과는 상위 30개(`RESULT_LIMIT`)까지만 돌려준다. 뜻 점수는 아무 조항에나 0보다 큰 값을
주기 때문에 그냥 두면 251개가 전부 딸려와 응답이 400KB가 된다.
AI가 보는 건 상위 8개(`lib/llm.ts`의 `CONTEXT_LIMIT`)뿐이다.

### 2-4. 분야를 나눠 섞는다 (261023)

**경기(야구규칙 + 리그 규정, 457개)와 규약(454개)을 따로 색인한다.** BM25 통계와 2-3의
"최댓값으로 나누기"도 분야마다 따로 한다. 그래서 경기 조각끼리의 순위는 규약을 넣기 전과 같다.
규약을 한 색인에 그냥 섞었을 때는 조각 수가 두 배가 되며 BM25 통계가 바뀌어, 규약과 상관없는
경기 질문 3개가 같은 경기 조각끼리 순서가 섞여 밀렸다(3절).

야구규칙과 리그 규정은 한 분야로 둔다. 서로 엮인 곳이 많고("몸에 맞는 공"이 리그 규정의 비디오
판독 대상 목록에도 있다) 지금까지 한 색인에서 문제가 없었다.

**둘 다 검색한 뒤 먼 쪽 분야의 점수를 깎는다.** 한쪽만 검색하면 판별이 틀렸을 때 정답이 아예
사라진다. 질문이 규약 쪽일 확률 p를 두 증거의 평균으로 정한다.

| 증거 | 계산 | 왜 |
|---|---|---|
| 뜻 | 질문 벡터와 분야별 평균 벡터(중심)의 유사도 차이를 시그모이드로 (`DOMAIN_MIDPOINT` 0.005, `DOMAIN_SPREAD` 0.015) | 시험 46문항에서 차이가 경기 -0.32~-0.004, 규약 +0.02~+0.08로 갈린다 |
| 글자 | 분야를 가리지 않은 색인으로 매긴 글자 검색 상위 5개 중 규약 조각 비율 | 뜻만 보면 `승부조작하면 어떻게 돼?`가 경기 쪽(-0.07)으로 판별된다. 그 분야에만 있는 말이 질문에 있으면 글자가 잡는다 |

더 그럴듯한 분야는 가중치 1, 다른 쪽은 `0.3 + 0.7 x (그쪽 확률 / 큰 쪽 확률)`. 확실하면 0.3까지
깎이고, 반반이면 둘 다 1이다.

분야별 색인끼리 BM25 점수를 바로 비교해 판별하지 않는 이유: 규약에는 "주자" 같은 경기 말이
드물어 그 분야 안에서 희귀도가 부풀려진다. 그래서 글자 증거는 전체를 한 색인으로 본 점수를 쓴다.
같은 색인이 질문 벡터가 없을 때(API 실패)의 비상 경로로도 쓰인다. 그때는 분야를 판별할 수 없어
규약을 그냥 섞었던 때와 같은 방식으로 돌아간다.

**시간은 거의 늘지 않는다.** 질문 벡터는 뜻 점수용으로 이미 만들고(API 1번), 판별은 내적 2번(0.002ms)이다.
글자 점수가 분야별 + 전체로 두 번이 됐지만 1ms 안쪽이다.

판별이 갈리는 경계 질문(시험 문항에는 없다, 261023에 손으로 확인):

| 질문 | 결과 |
|---|---|
| 외국인 선수도 비디오 판독 신청할 수 있어? | 리그 규정 제28조(판독 신청) 1등 |
| 부상자 명단에 올리면 며칠 뒤에 돌아와? | 리그 규정 제14조-3 1등, 규약 `외국인고용-제10조` 2등 |
| 승부조작하면 어떻게 돼? | 규약 제148조(부정행위) 1등 |
| 엔트리 몇 명이야? | 정답 리그 규정 제14조-6(29명) 3등 |

**조항 번호를 맞혔는지가 아니라, 답에 들어가야 할 내용이 들어갔는지를 본다.**

| 없는 조항 번호를 지어냄 | **0** | **0** |
| 함정에 답을 지어냄 | **0** | **0** |
| 모델 호출 평균 시간 | 5.6초 | 10.5초 (그날 무료 API가 느렸다) |

260929 측정에서 새 상황형 3문항은 모두 정답이었다. 다만 채점은 필요한 말이 들어갔는지만
본다. 화면에서 직접 물어보면 "베이스를 태그하면 아웃"이라고 맞게 말한 뒤 "태그 없이 그냥
지나갈 수 없습니다"를 덧붙여 헷갈리게 끝나는 답이 여전히 나온다(한계 8).

주의: `eval:answer`의 시간은 모델 호출만 잰 것이라 질문 임베딩 326ms가 빠져 있다.

틀렸을 때 검색 탓과 모델 탓을 가르는 기준은 **testset의 `expect`가 넘어갔는지**로 본다.
답이 맞았는지는 내용(`must`)으로 보고, 탓을 가르는 데만 `expect`를 쓴다.
(전에는 "빠뜨린 내용의 표현이 넘겨준 조항 본문에 있나"로 봤는데, `1루`나 `진루` 같은
흔한 말은 아무 조항에나 있어서 검색이 실패한 경우까지 모델 탓으로 넘어갔다.)

거부("찾지 못했습니다")는 **첫 문장만** 본다. 제대로 답해놓고 끝에 "이외의 경우는
찾지 못했습니다"를 덧붙인 답변까지 포기로 분류되던 문제가 있었다.

남은 실패:

- `낫아웃이 성립하는 경우는?` — 제3스트라이크를 제대로 다루지 못한다.
- `몸에 맞는 공이면 어떻게 돼?` — **검색 탓.** 정답 `5.06⒞`가 9등이라 넘어가지 않았다.
  모델이 "찾지 못했다"고 답한 것은 옳은 판단이다.
- `인필드 플라이는 언제 선언돼?` — 선언 시점은 맞게 말하나 성립 조건을 빠뜨린다.
- `세트 포지션이 뭐야?` — 자세 설명은 정확하다. "두 가지 정규투구자세 중 하나"라는
  맥락만 빠졌다. 채점이 빡빡한 쪽이지만 기준을 결과에 맞춰 무르게 고치지 않으려고 그대로 뒀다.
- `피치클락은 몇 초야?` — 23초와 18초는 말하나 타석간 33초를 빠뜨린다.
  넘겨준 `리그-부록-KBO피치클락규정-3`에 `타석간 시간 33초`가 표로 그대로 있었다.
- `타임은 언제 선언할 수 있어?` — 심판원과 선언 사유는 맞게 말하나 볼 데드를 빠뜨린다.

`낫아웃`은 원인이 뚜렷하다. 모델이 "낫아웃"을 **"not out"으로 직역해** "아웃 조항에
해당하지 않을 때"라고 답한다. 검색은 정답 `5.05⒜`를 1등으로 넘겼는데도 쓰지 않았다.
넘긴 8칸 중 6칸이 `5.09`(아웃 조항)라 그쪽으로 끌린 것으로 보인다.

## 4. 알려진 한계

### 한계 1. 사전은 사람이 적어둔 말만 커버한다

뜻 검색이 들어오면서 많이 완화됐다. `아웃이란 뭐야?`는 글자로는 23등이었는데
뜻으로는 1등이다. 하지만 반대 방향도 있다. `낫아웃`은 뜻으로만 찾으면 20등까지 밀리고
사전(글자 쪽)이 잡아줘야 1등이 된다.

**둘 중 하나만으로는 안 되고, 사전은 여전히 필요하다.**

### 한계 2. 제목이 조각마다 복제돼 있다 — 261023에 고침

긴 조항을 ⒜·⑴ 단위로 쪼갤 때 부모 제목을 그대로 물려줘서, 457조각 중 285개가 제목을
나눠 쓰고 있었다(5.09에서 나온 37개가 모두 "아웃", 리그 규정 "KBO 표창규정" 22개 등).

**쪼갠 조각 제목에 자기 항목의 머리말을 붙인다**(`build_rules.py`, `build_league.py`).

```
5.09⒝⑸  아웃  ->  아웃 · 페어 플라이 볼, 파울 플라이 볼이 정규로 포구된 뒤…
5.06⒞    주루  ->  주루 · 볼 데드
리그-제28조-3  비디오 판독  ->  비디오 판독 · 비디오 판독 대상 플레이
```

리그 규정은 다른 장에 같은 이름으로 있는 조항(정규시즌·한국시리즈·퓨처스리그의 "경기방식" 등
30개)에 장 이름을 붙인다: `경기방식 (KBO 한국시리즈)`. 이제 457개 중 455개가 서로 다른 제목이다
(남은 2개는 원래 다른 두 조항인 "베이스 코치").

PDF 원문이 저장소에 없어서 이미 만든 JSON에 같은 규칙을 적용하는 `--retitle`을 뒀다.
조각 본문에 각 단계의 항목 줄("⒝ 주자 아웃", "⑸ 페어 ...")이 남아 있어 빌드 때와 같은
제목을 만든다. `python build_rules.py --retitle data/rules.json`. 제목이 바뀌면 뜻 벡터(제목+본문)와
형태소 파일도 다시 만든다(`npm run build:vectors`, `npm run build:tokens`).

| 51문항 | 고치기 전 | 머리말을 이어 붙임 | **자기 항목 머리말만 (채택)** |
|---|---|---|---|
| 시험 39 (8개 안) | 38 | 38 | **39** |
| 시험 39 평균 순위 | 1.9등 | 2.2등 | 1.9등 |
| 시험 밖 12 평균 순위 | 3.4등 | 2.4등 | 2.6등 |
| `보크가 뭐야?` | 1등 | **14등** | 1등 |

- **이어 붙이면 안 된다.** "투수의 반칙행위 · 보크 · ..."처럼 중간 단계 머리말까지 붙이자 6.02⒜(보크)
  아래 조각 13개가 모두 제목에 "보크"를 가져 정의-3을 밀어냈다. 형제 조각이 같은 말을 나눠 쓰면 원래
  문제가 다시 생긴다.
- 크게 오른 것: 타구가 주자에 맞은 질문들(`타자가 친 공이 주자 몸에 맞았는데` 10등 -> 2등, `투구가 타자 옷에
  스치면` 7등 -> 1등, `땅볼이 2루 주자 발에` 8등 -> 4등). 내린 것은 대부분 한두 칸이고, 가장 큰 건
  `포수가 세 번째 스트라이크를 놓쳤는데` 5등 -> 8등, 짧은 끝내기 2등 -> 5등이다(둘 다 8개 안).
- **"한 조항이 상위권을 독점한다"는 지표는 거의 그대로다**(상위 8개 안의 서로 다른 조항 4.80 -> 4.73개).
  그런데 독점이 심한 질문을 보면 `자책점`, `비디오 판독`, `피치클락`처럼 원래 한 조항에 대한 질문이라
  그 조항의 조각들이 상위를 채우는 게 맞고, 셋 다 정답을 찾는다. 효과는 독점이 아니라 정답 순위에서 났다.

### 한계 3. 문서를 추가하면 사전 항목이 조용히 꺼질 수 있다

확장은 '규칙집이 거의 쓰지 않는 말'에만 걸린다(`RARE_MAX_DOCS = 2`). 그래서 문서를
새로 넣으면 그 말이 흔해져 항목이 저절로 멈춘다.

리그 규정을 넣자 `비디오 판독 대상 플레이` 목록에 "⑤ 몸에 맞는 공"이 글자 그대로
들어 있어서, "몸에 맞는 공"이 2개 조항에서 나오게 됐다. 경계선이라 아직 작동하지만
하나만 더 늘면 꺼진다.

`lib/search.ts`가 색인을 만들 때 확인해서 꺼진 항목이 있으면 로그로 알린다.

### 한계 4. 점수에 절대 기준이 없다

**"검색이 실패했다"를 점수로 판단할 수 없다.** 문턱을 세울 자리가 없다.

| | 답 있는 질문의 최저점 | 답 없는 질문의 최고점 |
|---|---|---|
| 글자 점수 | 0.050 | 0.242 (순서가 뒤집힘) |
| 뜻 점수 | 0.168 (`병살이 뭐야?`) | 0.188 (`FA 자격 요건이 뭐야?`) |

뜻 점수는 적어도 순서는 맞지만 0.168과 0.188 사이에 선을 긋는 건 너무 아슬아슬하다.
(다만 `FA 자격 요건`은 야구규약 PDF에 답이 있는 질문이라 진짜 함정은 아니었다.
261023에 규약을 넣어 지금은 정답이 있다. 이 표는 그 전에 잰 것이다.)

이 때문에 검색이 실패해도 8개를 꽉 채워 AI에게 넘기고, AI는 실패한 줄 모른 채
받은 조항으로 답을 만든다. `lib/llm.ts` 프롬프트에 "추측하지 말고 찾지 못했다고 답하라"가
이미 있지만, AI 입장에서는 자료를 받았으므로 발동하지 않는다.

### 한계 5. 긴 조각은 앞부분만 벡터로 만든다

조각 하나가 최대 4,248자인데 임베딩 모델의 입력 길이에 한도가 있어
앞 1,200자만 쓴다(`scripts/build-vectors.mjs`의 `MAX_CHARS`).
뒷부분에만 답이 있는 조항은 뜻 검색으로 못 찾는다. 글자 검색이 그걸 메운다.

### 한계 6. 쓸 수 있는 임베딩 모델이 하나뿐이다

NVIDIA 목록에는 임베딩 모델이 7개 있지만 이 계정에서 6개는 404가 난다.
`nvidia/nemotron-3-embed-1b` 하나만 열려 있다.

### 한계 7. 상황을 풀어 쓴 질문은 사람 말 설명이 있는 조항만 잡힌다

규칙집은 상황을 법조문 말투로 적는다("베이스에 다시 닿기 전에 신체 또는 그 베이스에
태그당한 경우"). 사람은 "베이스를 밟고 있지 않은 주자는 태그 안 해도 돼?"라고 묻는다.
글자도 안 겹치고, 질문에 든 `라인드라이브`·`태그` 같은 단어가 그 용어의 **정의** 조항을
1·2등으로 끌어올려 정답을 밀어낸다.

사람 말 설명(`data/plain.json`)으로 푼다. 지금은 5.09⒝⑸ 하나뿐이라 다른 상황 질문은
여전히 같은 문제를 겪는다.

### 한계 8. 조항을 넘겨받아도 작은 모델은 상황에 대입하지 못한다

5.09⒝⑸가 4등으로 넘어간 뒤에도 gpt-oss-20b는 5번 중 5번 "찾지 못했습니다"라고 답했다.
조항이 "플라이 볼이 포구된 뒤"라고만 적혀 있어 라인드라이브와 연결하지 못한 것이다.
사람 말 설명을 AI에게도 같이 주자 5번 모두 이 조항을 근거로 들었다. 다만 결론을
"베이스만 밟아도 아웃"과 "태그를 받아야 한다"로 섞어 말하는 답이 5번 중 1번 남았다.

## 5. 시도했다가 채택하지 않은 것

같은 실험을 반복하지 않기 위해 남긴다. 따로 적지 않은 것은 `data/testset.json` 26문항으로 측정했다.

### 글자 점수를 형태소 분석 + BM25로 — 채택 (261007)

글자를 두 개씩 겹쳐 자르는 방식은 뜻 없이 글자만 겹친다. 질문에 "라인드라이브"가 있으면
라인 드라이브의 '정의' 조항을, "몸에 맞는 공"이 있으면 그 말이 든 비디오 판독 목록을,
"주자·안타"가 있으면 5.05를 끌어올려 정답을 밀어냈다. 질문마다 사람 말 설명을 붙여 고치던
것도 사실은 이 글자 점수를 정답 쪽으로 맞춰준 것이었다.

한국어 검색 실무는 형태소 분석 + BM25를 쓴다(Elasticsearch의 nori 등). 같은 한국어 검색
시험(MIRACL)에서 형태소 분석 BM25가 NDCG 0.61~0.64, 단어 경계만 자르는 방식이 0.41이라는
비교가 있다. 형태소 분석기 셋을 우리 데이터로 재봤다. 뜻 점수, 사전, 사람 말 설명, 섞는
비율은 그대로 두고 글자 점수만 바꿨다. 시험 밖 12문항은 설명이나 사전을 보기 전에 새로 쓴
질문이다.

| 글자 점수 | 시험 39문항 (8개 안) | 시험 밖 12문항 (8개 안) | 시험 밖 평균 순위 |
|---|---|---|---|
| 글자 두 개씩 + TF-IDF (이전) | 38 | 10 | 7.2등 |
| **oktjs + BM25 (채택)** | 38 | **11** | 4.7등 |
| Kiwi + BM25 | 37 | 10 | **3.7등** |

- **mecab-ko-wasm**은 사전이 들어 있지 않아 실행되지 않았다.
- **Kiwi**는 분석이 가장 정확하고("공이면"을 공+이면으로 나눈다) 평균 순위도 가장 좋았지만,
  oktjs와 차이가 1~2문항 수준이라 우열이라 보기 어렵다. 대신 배포 부담이 크다. 모델 파일이
  105MB(가장 큰 파일 75.9MB, GitHub는 100MB부터 푸시를 막는다)이고, 불러오면 Node 메모리가
  약 990MB가 된다(Vercel 무료 플랜 함수 한도 2GB, oktjs는 약 350MB). 모델 파일은
  `outputFileTracingIncludes`로 따로 실어야 해서, 빠뜨리면 운영에서만 검색이 죽는다.
- **oktjs**는 사전을 품은 순수 자바스크립트 파일 하나(3.4MB)라 npm 설치만 하면 된다.
  2023년 이후 업데이트가 없는 게 흠이다. 분석기를 바꿀 때는 `lib/tokenizer.ts`만 고치고
  `npm run build:tokens`를 다시 돌리면 되게 해뒀다.

바꾼 뒤 1등으로 찾은 문항이 24 -> 25. 사용자가 실제로 물었다가 틀린 답을 받은 질문들이 특히
올랐다. 짧은 끝내기 질문 7.01이 6등 -> 2등, 라인드라이브 5.09⒝⑸가 4등 -> 2등, 직선타 2등 -> 1등.
영어 질문(`infield fly`, `balk` 1등, `wild pitch` 2등)도 그대로 찾는다. `next build` 후 운영
서버로 띄워 검색과 답변이 되는 것까지 확인했다.

**바꾼 뒤 내려간 문항을 따로 봤다.** 원인이 셋이었고 셋 다 질문 하나가 아니라 방식의 문제였다.

| 원인 | 증상 | 고친 방법 |
|---|---|---|
| 제목과 영문명을 한 칸에 합침 | 영문명이 있는 정의-54("아웃" + "OUT")가 제목이 "아웃"뿐인 5.09 조항 22개에 밀림. `아웃이란 뭐야?` 1등 -> 8등 | 원래 방식대로 따로 매겨 높은 쪽 |
| oktjs가 "2루"를 "2"와 "루"로 나눔 | "루"(116개 조항), "2"(191개)가 흔한 말이 돼 제목이 "각 루(1, 2, 3루)"인 2.03이 "2루"가 든 질문마다 1등. `땅볼이 2루 주자 발에 맞았어` 7등 -> 23등 | 숫자 바로 뒤에 붙은 명사는 한 낱말로("2루", "2아웃", "1사", "4구") |
| 사람은 "맞다", 규칙집은 "닿다" | 위 땅볼 질문은 정답 5.09⒝⑺과 겹치는 낱말이 "주자", "아웃"뿐. 이전 7등도 제대로 찾은 게 아니라 글자 점수가 다 고르게 낮아 뜻 점수로 올라간 것 | 질문에 "맞다"가 있으면 "닿다"도 찾는다. 규칙집도 두 말을 다 쓴다("새에게 맞았을 경우", "페어 볼에 닿았을 경우"). 조항 쪽은 "규정에 맞게" 같은 다른 뜻이 있어 건드리지 않는다 |

| | 시험 39 (8개 안) | 시험 밖 12 (8개 안) | 시험 밖 평균 |
|---|---|---|---|
| 글자 두 개씩 (이전) | 38 | 10 | 7.2등 |
| BM25 1차 | 38 | 11 | 4.7등 |
| + 영문명 분리 | 38 | 10 | 4.8등 |
| + 숫자 단위 묶기 | 38 | 11 | 4.2등 |
| **+ 맞다/닿다 (지금)** | **38** | **12** | **3.4등** |

이전보다 내려간 문항은 4개이고 전부 한 칸 차이다(1->2, 2->3, 4->5, 7->8).

**답도 재봤다.** 사용자가 실제로 물었던 질문을 여러 번 물어 결론이 맞는지 직접 읽고 판정했다
(자동 채점은 "종료"라는 낱말이 없으면 '일부'로 쳐서 쓰지 않았다). 프롬프트는 같고 검색만 다르다.

| 질문 | 이전 검색 (261007 오전) | 지금 |
|---|---|---|
| 끝내기, 긴 질문 | 6/8 (빈 답 1) | 7/8 |
| 끝내기, 짧은 질문 | 0/8 (빈 답 2) | 4/8 |
| 라인드라이브 | - | 6/6 |

짧은 질문은 정답 7.01이 6등 -> 2등이 되면서 나아졌다. 남은 오답은 "주자 둘이 들어오면 7:5"라는
모델의 추론 실수다.

### 조항 전체에 AI가 만든 설명 붙이기 — 효과 없음 (261007)

손으로 붙인 사람 말 설명이 효과가 커서(16등 -> 4등, 9등 -> 1등), 질문마다 손으로 붙이는
대신 457개 전부에 gpt-oss-20b로 만들어 붙여봤다(`scripts/build-auto-notes.mjs`,
`data/plain-auto.json`). Anthropic의 Contextual Retrieval과 같은 생각이다(조각에 맥락
설명을 붙이면 검색 실패가 35~49% 줄었다고 한다).

시험 39문항과, 설명을 보기 전에 새로 쓴 시험 밖 질문 12개로 쟀다.

| 자동 설명 쓰는 방식 | 시험 39문항 | 시험 밖 12문항 |
|---|---|---|
| 안 씀 | 38 | **10** (평균 7.2등) |
| 뜻 점수에만 (설명 벡터를 따로, 원문과 높은 쪽) | 38 | 9 (7.7등) |
| 글자 점수에만 (본문 뒤에 붙여 색인) | 38 | 10 (7.2등) |
| 둘 다 | 38 | 8 (8.1등) |
| Anthropic 방식 (설명+원문을 합쳐 벡터) | 37 | 9 (7.3등) |
| 원문 벡터와 합친 벡터 중 높은 쪽 | 38 | 8 (7.4등) |

**전부 같거나 나빴다. 쓰지 않는다.** 손으로 붙인 설명은 틀린 질문의 정답 조항 하나만
끌어올려 효과가 있었지만, 전부에 붙이면 모든 조항이 비슷한 말투의 글("~할 때 적용된다",
"주자", "아웃")을 하나씩 더 가져 같이 올라가고 차이가 사라진다. 만든 설명에 틀린 내용도
섞여 있었다(5.05⒜에서 "포수"를 "투수"로 쓰고 핵심 조건인 "1루가 비었거나 2아웃일 때"를
빠뜨림, 1.04에서 "한 번의 타격으로 홈까지"라는 없는 조건을 붙임). 처음 지시문에 든 예시
("플라이 볼과 뜬공")가 상관없는 조항 설명에 그대로 섞이는 일도 있어 예시는 뺐다.

같은 날 실무에서 쓰는 다른 방법도 우리 데이터로 재봤다.

- **점수 섞기를 RRF(순위 기반, Azure AI Search·Elasticsearch 기본값)로:** 38 -> 36. 낫아웃이
  1등 -> 25등. 지금의 "각자 최고점으로 나눠 반반"이 낫다.
- **뜻 점수 비중 0.5 -> 0.6~1.0:** 38 -> 36~38. 끝내기·라인드라이브는 오르지만 낫아웃이
  뜻만으로는 60등까지 무너진다.
- **재정렬(리랭커) 모델:** NVIDIA 무료 API의 리랭커가 2026-05-18에 종료됐다(410).

남은 후보는 글자 점수를 **형태소 분석 + BM25**로 바꾸는 것이다(-> 같은 날 채택, 아래). 한국어 검색 실무는 보통
이렇게 하고, 지금처럼 글자 두 개씩 자르는 방식보다 정확도가 크게 높다고 알려져 있다
(MIRACL 한국어에서 형태소 분석 BM25가 NDCG 0.61~0.64, 단어 경계만 자르는 방식이 0.41).

### 몸에 맞는 공 — 사람 말 설명으로 9등 -> 1등 (261007)

`몸에 맞는 공이면 어떻게 돼?`가 9등이었던 건 사전 탓이 아니었다. 사전 항목은 그대로
작동했다("몸에 맞는 공"은 규칙집 2개 조항에만 나와 경계선 안). 리그 규정의 비디오 판독
대상 목록(리그-제28조-3)에 "⑤ 몸에 맞는 공"이 글자 그대로 있어 3등으로 끼어든 게 원인이다
(5절 "리그 규정을 넣은 대가"). 같은 말이 다른 조항에 있어서 생긴 문제라 사전으로는 못 푼다.

5.06⒞에 사람 말 설명(⑴ 투구가 타자의 몸·옷에 닿으면 볼 데드, 타자는 1루, 밀리는 주자는
진루)을 붙였다.

**"몸 맞는 공" 같은 표현 차이는 사전에 넣지 않는다.** 넣었다 뺐다 하며 재보니 뜻 점수가
알아서 잡았다(아래 표의 시험 밖 표현 셋은 사전 없이 잰 것). 차이가 난 건 `몸 맞는 공
맞으면 타자는?`(사전 있으면 3등, 없으면 11등) 하나뿐이었다. 사전은 규칙집에 아예 없는
은어(낫아웃, 데드볼)에만 쓴다. "사구"도 넣지 않는다. 규칙집에 "4사구"로 21개 조항에
나와 사전이 꺼지고, 볼넷까지 섞인다.

**글자 수나 "한 글자 차이" 같은 규칙으로 비슷한 말을 묶지도 않는다.** 한 줄만 적으면
"몸 맞는 공"까지 잡히게 하려고 해봤지만, 한 글자로 뜻이 바뀌는 말이 있어 반드시 틀린다.
비슷한 표현은 뜻 점수(임베딩 모델)가 판단한다.

이참에 사전의 중복을 지웠다. 띄어쓰기는 원래 무시하므로 "낫 아웃", "고의 사구", "몸에맞는공",
"자동고의4구"는 다른 항목과 같은 말이고, "스트라이크아웃 낫아웃"은 "낫아웃"을 품고 있다.

|---|---|---|---|
| 4개 | 20/27 (74%) | 5.7초 | 2건 |

### 답변을 인용 조항 번호로 채점하기 — 260912에 폐기

처음에는 답변 끝의 인용 번호를 `expect`와 대조해 채점했다. 파서를 고쳐 조항이
제대로 쪼개지자 이 방식이 무너졌다.

**정당한 정답이 여러 개가 됐다.** `세트 포지션이 뭐야?`의 `정의-70`은 내용이
"두 가지 정규투구자세 가운데 하나다"가 전부다. 모델이 실제 설명이 있는 `5.07⒜⑵`를
골랐는데 오답이 됐다. `자책점`은 `expect`가 `9.16⒝`(자책점이 되지 않는 예외)였는데
진짜 계산법인 `9.16⒜`는 그때 데이터에 없어서 그렇게 적혀 있던 것이었다.

**가짜 정답도 나왔다.** `낫아웃이 성립하는 경우는?`에 모델이 `5.05⒜⑴`을 인용해
"부분 정답" 처리됐는데, 답변 내용은 제3스트라이크를 한 번도 언급하지 않은 엉뚱한
글이었다. 번호만 그럴듯하면 통과하는 구멍이 있었다.

**필요한 내용이 조항 하나에 없는 경우도 있다.** `투수가 이물질을 바르면`은 금지
행위가 `6.02⒞`에, 벌칙(즉시 퇴장)이 `6.02⒟`에 나뉘어 있다.

인용 채점을 완전히 버리지는 않았다. "규칙집에 없는 번호를 댔는가"는 그대로 센다.
데이터에서 조항 11개가 빠진 걸 찾아낸 게 바로 이 숫자였다.

### 리그 규정을 넣은 대가 — 질문 하나가 밀렸다

대상 플레이 목록에 "⑤ 몸에 맞는 공"이 글자 그대로 있어 **노이즈가 아니라 진짜 관련
조항이다.**

사전 확장어를 늘려 되돌리려 했으나 전부 더 나빠졌다. (9등 -> 14등, 19등)
짧은 확장어 하나가 최선이라는 앞의 결론이 다시 확인됐다.

### 규약을 넣은 대가 — 조각이 두 배, 3문항이 조금 밀렸다 (261023)

조각이 457개에서 911개로 늘었지만 기존 문항 중 상위 8개 밖으로 밀린 것은 없다.

사전 항목도 꺼지지 않았다(한계 3). 규약을 넣은 뒤에도 `몸에 맞는 공`, `데드볼`은
